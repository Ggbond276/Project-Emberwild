# 32. 用 Werewolf 搭建第二只怪物 AI（分阶段手册）

> **这份手册的前提**：框架保持在 `a6ec796`，**不重构、不抽象、不做通用框架**。
>
> 你要做的就是一件事：**在现有架构里，把 Werewolf 这只怪跑起来。**
>
> 跑通之后，我们再回头看"为什么现在还不该抽象"。

## 版本说明（第五版，当前）

本手册改过四轮。**如果你是按旧版做的，请对照下表调整。**

### 第四次改动（最重要）：把契约真正落到代码里

前三版最大的问题是**嘴上说"命名契约"，代码里仍是 Shell 专属命名**：

```csharp
public interface IEnemyAnimator
{
    void SetRoll(bool roll);      // ← Roll 是螃蟹的招式名
    void SetHidden(bool hidden);  // ← 缩壳是螃蟹的专属能力
    void PlayAttack();            // ← 写死"只有一种近战"
    // ...
}
```

**这导致三个后果**：

1. 接口里有怪物专属的方法 → 狼人被迫实现空方法
2. 每只怪要写一个实现类（`ShellAnimator` / `WerewolfAnimator`）
3. 契约只存在于文档里，代码完全没有体现

**第四版的做法**：

| 改动 | 内容 |
|---|---|
| **Shell 控制器改名** | 6 个参数改成契约名（`Speed`→`MoveSpeed`、`Roll`→`Dash`、`IsHidden`→`Stance` 等） |
| **接口收敛** | 8 个方法 → **4 个**（`SetMoveSpeed` / `PlayAction` / `SetState` / `SetDead`） |
| **实现类合并** | `ShellAnimator` + `WerewolfAnimator` → **一个 `EnemyAnimator`** |
| **契约代码化** | 参数名集中在一张静态字典里，不再散落各处的字符串字段 |

**收益**：新增怪物需要写的 C# 从 200 行变成 **0 行**。

> **顺序很重要：先统一命名（阶段 0），再合并实现（阶段 3）。**
> 反过来做不了。

### 第五次改动：动作参数改成枚举

第四版虽然收敛了接口，但 `PlayAction(string actionId)` 和 `SetState(string stateId)` 用的还是字符串。

**问题**：

```csharp
animator.PlayAction("mele");    // 少个 e
```

**编译通过**，运行时静默忽略——这是最难排查的一类 bug。

**为什么第四版会犯这个错**：我当时用"枚举序列化会错位"来反对枚举。
但那个论证只适用于**存进 `.asset` 的字段**（如 `EnemyStateType action`）。
`PlayAction` 的参数是**代码内部传递**，从不落盘，所以枚举完全没有风险。

**第五版的做法**：

```csharp
void PlayAction(EnemyAction action);           // 枚举
void SetState(EnemyStateFlag state, bool);     // 枚举
```

| 收益 | 说明 |
|---|---|
| 拼错编译不过 | `EnemyAction.Mele` 直接报错 |
| IDE 补全 | 打 `.` 就列出 8 个动作 |
| 新增动作 | 加枚举值，所有 `switch` 会被 IDE 标出未覆盖 |
| 漏写映射 | `AssertContractSize()` 在 Awake 立刻报错 |

**同时明确了两套枚举的边界**：

- `EnemyStateType`（13 个）→ **存进资产**，改顺序会错位，只能往后加
- `EnemyAction` / `EnemyStateFlag`（8 + 2）→ **只在代码里传**，随便改

> **判断依据**：**会落盘的枚举对顺序敏感，只在内存里传的随便改。** 这两类不要混。

### 三轮分别为什么改

**第一版 → 第二版：动作进入方式**
从 Locomotion 出发意味着"Alert 播到一半想攻击必须等它播完"。
10 个动作状态要互相打断就得连 O(n²) 条交叉过渡。改成 AnyState 后，动作间天然可打断。

**第二版 → 第三版：转向彻底移出动画系统**
第二版把转向做成 2D BlendTree 的一维，虽然能用，但引入了一整套复杂度：
2D 坐标摆放、`Turn Left` / `Turn Right` 两个 Motion、"动画播完 vs 角度转够"的不同步问题。

第三版直接交给 `CustomNavAgent.turnSpeed`：

```
Agent.SetDestination(目标) → Agent 按 turnSpeed 旋转 transform.forward
```

**代价是零**——`turnSpeed` 本来就是配置项。收益是整块复杂度消失：
参数少 1 个、Motion 少 2 个、代码状态少 1 个、配置字段少 1 个、条件少 1 个。

**如果你已经按第二版把 Locomotion 做成 2D：**

1. Blend Type 改回 **`1D`**，Parameter 只留 `MoveSpeed`
2. 删掉 `Turn Left` / `Turn Right` 两行 Motion（只留 Idle / Walk / Run）
3. Parameters 面板删掉 `Turning`
4. 如果建过 `TurnToTarget` 状态，删掉它
5. 确认 `CustomNavAgent.turnSpeed` 有值（建议 10~15）

**那 `Turn Left` / `Turn Right` 两个动画就浪费了吗？**

是的，本项目不用它们。**这符合"不为用而用"的原则**：

> 动画该不该进状态机，看它是不是"一个独立的、需要被代码触发的动作"。
> 攻击、受击、死亡是。转身不是——它是移动的连续过程，由寻路系统负责。

# 阶段 0：命名契约与 Shell 改造

## 目标

这一步**不改 AI 逻辑，但要改 Shell 的控制器和动画类**。

改完之后你要能回答三个问题：

1. Shell 是靠哪几个组件跑起来的？
2. 它的 Animator 有几个参数、哪几个不合规？
3. 为什么"给 Shell 的参数改名"是给 Werewolf 铺路？

## 为什么先做这个

因为**命名是唯一会传染的东西**。

参数名错了，可以改；命名规范错了，会传染到你写的每一个状态、每一个行为树节点。
  
第 3 只怪、第 4 只怪都会沿用你今天的错误命名。

而且——你现在不改命名，第 2 只怪就会变成"Shell 一套名字、Werewolf 另一套名字"，
  
以后每加一只怪就多一套，最后没法统一。

## 步骤 0.1：盘点 Shell 的组件

打开 `Assets/Resources/Prefabs/Monsters/Shell.prefab`，看 Inspector。它挂了 7 个组件：

| 组件                | 职责                                | 一句话                              |
| ----------------- | --------------------------------- | -------------------------------- |
| `CombatAttribute` | 存血量/攻防                            | **数值仓库**                         |
| `EnemyEntity`     | 数据表 ↔ 数值仓库的桥                      | **查表器**（TID → HP/AD/DEF/SubType） |
| `CustomNavAgent`  | 寻路移动                              | **腿**                            |
| `EnemyPerception` | 找目标、算距离                           | **眼睛**                           |
| `EnemyCombat`     | 发起攻击、发事件                          | **手**                            |
| `EnemyBrain`      | 每帧驱动，切状态                          | **大脑/总调度**                       |
| `ShellAnimator`   | 把"播放攻击"翻译成 `SetTrigger("Attack")`（**阶段 3 会被替换成通用类**） | **翻译官** |

**这里有一个必须理解的层级关系**：

```
EnemyBrain（总调度）
  ├─ 依赖 EnemyPerception  → 写 BB（黑板）
  ├─ 依赖 EnemyCombat      → 发攻击事件
  ├─ 依赖 CustomNavAgent   → 移动
  ├─ 依赖 IEnemyAnimator   → 播动画（阶段 3 之后统一由 EnemyAnimator 实现）
  └─ 依赖 EnemyEntity      → 拿 MaxHp / SubType
```

`EnemyBrain` 是**唯一**知道所有组件的地方。其他组件之间**互不认识**。
  
这是现有框架最重要的一条性质，后面所有改动都要遵守。

## 步骤 0.2：盘点 Shell 的 Animator 参数（以及它的设计缺陷）

打开 `Assets/Animators/Shell_Used.controller`，Parameters 面板有 8 个：

| 参数 | 类型 | 谁在用 | 合规吗 |
|---|---|---|---|
| `Speed` | Float | 移动 BlendTree | ❌ 太泛 |
| `IsDead` | Bool | 死亡 | ✅ |
| `IsHidden` | Bool | 缩壳 | ❌ 写死了具体能力 |
| `Attack` | Trigger | 近战 | ❌ 没有类别概念 |
| `ProjectileAttack` | Trigger | 远程 | ❌ 写的是实现方式 |
| `CastSpell` | Trigger | 施法 | ❌ 动词 + 名词冗余 |
| `TakeDamage` | Trigger | 受击 | ✅ |
| `Roll` | Bool | 滚动 | ❌ 写的是招式名 |

**8 个里只有 2 个合规。**

### 这 6 个不合规的名字，会带来什么实际问题

假设你只有一个 Shell，这些名字"能用"。但一旦有第二只怪，问题立刻暴露：

| 名字 | 具体问题 |
|---|---|
| `Speed` | 三个月后你看到 `Speed`，不知道是移动速度、攻击速度、还是动画播放速度 |
| `Attack` | 狼人有 4 种近战（咬/左斩/右斩/重击），都叫 `Attack` 就分不开 |
| `ProjectileAttack` | 如果哪天改成火球/声波/箭矢，这名字就错了，但动画逻辑没变 |
| `Roll` | 狼人也会"冲刺位移"，但它叫 Pounce 不叫 Roll。同一类动作两个名字 |
| `IsHidden` | 石像鬼会"石化"、史莱姆会"融化"，本质都是"进入防御姿态"，但这名字不通用 |
| `CastSpell` | `Cast` 和 `Spell` 表达同一件事，而且和 `Attack` 的命名不对称 |

**最关键的一条**：这些名字全部是**招式名 / 实现细节**，
所以代码里就不得不为每只怪写一个实现类（`ShellAnimator`、`WerewolfAnimator`…）。

**这就是本手册要解决的核心问题。**

## 步骤 0.3：建立参数命名契约（v2）

契约不是"建议"，是**代码里的强约定**。分四类，每类对应一个接口方法：

| 类别 | 接口方法 | 参数名 | 类型 | 说明 |
|---|---|---|---|---|
| **移动强度** | `SetMoveSpeed(float)` | `MoveSpeed` | **Float** | 0~1，驱动 Idle/Walk/Run 混合 |
| **一次性动作** | `PlayAction(string)` | `Melee` | Trigger | 近战（可以是多段动画串成） |
| | | `Heavy` | Trigger | 重击，慢且伤害高 |
| | | `Pounce` | Trigger | 中距离突进攻击 |
| | | `Leap` | Trigger | 远距离跳跃攻击 |
| | | `RangedAttack` | Trigger | 远程攻击 |
| | | `Spell` | Trigger | 施法 / 增益 |
| | | `Alert` | Trigger | 警戒 / 刚发现目标 |
| | | `TakeDamage` | Trigger | 受击 |
| **可逆持续状态** | `SetState(string, bool)` | `Dash` | Bool | 冲刺位移（可开关） |
| | | `Stance` | Bool | 防御姿态（缩壳/石化/融化都归它） |
| **死亡** | `SetDead(bool)` | `IsDead` | Bool | 终态，只置 true |

**一共 12 个参数名，4 个接口方法。**

### 为什么死亡单独一个方法，不并进 SetState

技术上 `IsDead` 也是 Bool，如果给它加个 `EnemyStateFlag.Dead` 也能工作。

但**语义上必须分开**：

```csharp
// 如果合并，会写出这样的代码
animator.SetState(EnemyStateFlag.Dead, false);   // ← 想复活？但框架没实现复活
```

死亡是**不可逆**的。用独立方法 `SetDead(bool)` 表达"这个只能设 true"，
调用方看到它就明白不该传 false。

> 这是"用 API 形状表达语义约束"的例子：
> 不是靠注释提醒，是靠**方法签名本身**让人无法误用。

### 五条命名规则

**规则 1：类别优先于招式**

```
❌ Bite / Slash / Claw      ← 招式名，每只怪都不一样
✅ Melee                    ← 类别名，狼人咬 / 螃蟹夹 / 骷髅挥剑都叫 Melee
```

代码不该知道"这只怪用牙还是用爪子"。它只需知道"我要打一下"，具体播哪个动画是 Animator 的事。

**规则 2：不写实现方式**

```
❌ ProjectileAttack   ← 改成火球/声波/箭矢就错了
✅ RangedAttack       ← 只说"远程"，不说"用什么"
```

**规则 3：`Trigger` 只给一次性动作，`Bool` 只给可逆持续状态**

| 动作 | 该用 | 为什么 |
|---|---|---|
| 攻击、受击、施法、警戒 | **Trigger** | 播一次就结束，不需要"取消" |
| 冲刺、姿态 | **Bool** | 需要持续保持，且要能主动结束 |
| 死亡 | **Bool** | 锁死到结束（但走独立方法） |

**判断方法一句话**：**这个动作需要"取消/关闭"吗？需要 → Bool，不需要 → Trigger。**

反过来会怎样：用 Trigger 做姿态 → 进去出不来；用 Bool 做攻击 → 忘了置回 false 就卡住。

**规则 4：代码里用枚举传递动作，不用字符串**

这个规则改过一次，值得说明。

**初版写法（错的）**：

```csharp
void PlayAction(string actionId);      // "melee" / "heavy" / ...
```

**为什么当时觉得对**：因为参数名（`Melee`）是给 Animator 用的字符串，id 是小写简写，
两者之间靠一张字典映射，用字符串很"统一"。

**为什么其实是错的**：

| 问题 | 用字符串 | 用枚举 |
|---|---|---|
| 拼错 `"mele"` | **编译通过**，运行时静默忽略 | 编译不过 |
| IDE 自动补全 | ❌ | ✅ |
| 改名重构 | 全项目搜索替换，容易漏 | 重命名一键完成 |
| 有哪些可选值 | 要翻代码或文档 | 点 `.` 就列出来 |
| 新增一个动作 | 加字典项，忘了加就运行时静默失败 | 加枚举值，`switch` 缺分支会有警告 |

**最关键的一点：我之前用"枚举序列化不安全"来反对枚举，那个论证用错了地方。**

那个论证的正确适用范围是"**存进 `.asset` 的字段**"——比如行为树节点里的 `action` 字段，
它存的是枚举的整数值，改动枚举顺序会让旧资产静默错位。

但 `PlayAction` 的参数是**代码内部传递的**，**从不进入资产**。
所以序列化风险根本不存在，用枚举只会更安全。

> **这条经验值得记住**：
> "枚举有问题"只针对"落盘的数据"，不针对"运行时的参数"。
> 把两者混为一谈，会让你在本该用枚举的地方退化成字符串。

**定稿设计**：

```csharp
/// <summary>一次性动作（Animator Trigger）。</summary>
public enum EnemyAction
{
    Melee,          // 近战（可含连段）
    Heavy,          // 重击
    Pounce,         // 突进攻击
    Leap,           // 跃击
    Ranged,         // 远程攻击
    Spell,          // 施法
    Alert,          // 警戒
    TakeDamage,     // 受击
}

/// <summary>可逆持续状态（Animator Bool）。</summary>
public enum EnemyStateFlag
{
    Dash,           // 冲刺位移
    Stance,         // 防御姿态
}
```

**新增一个动作 = 在 `EnemyAction` 加一个值 + 在映射表加一行。**
漏了映射表会有编译期警告（`switch` 未覆盖所有分支），不会再静默失败。

### 为什么动作和状态要分成两个枚举

看到这里你可能会问：`EnemyStateType` 已经有 13 个值（`AttackMelee` / `Hit` / `Pounce`…），
为什么还要单独搞一个 `EnemyAction`？不是重复吗？

**不是重复，是不同层次。** 看它们的对应关系：

| `EnemyStateType`（AI 状态） | 进去后播什么 |
|---|---|
| `Idle` | 无动作 |
| `Chase` | 无动作（只设 `MoveSpeed`） |
| `Dead` | `IsDead`（Bool，不是 Trigger） |
| `RollChase` | `Dash`（Bool） |
| `Hide` | `Stance`（Bool） |
| `AttackMelee` | `EnemyAction.Melee` |
| `AttackHeavy` | `EnemyAction.Heavy` |
| `Pounce` | `EnemyAction.Pounce` |
| `Leap` | `EnemyAction.Leap` |
| `AttackRanged` | `EnemyAction.Ranged` |
| `CastSpell` | `EnemyAction.Spell` |
| `Alert` | `EnemyAction.Alert` |
| `Hit` | `EnemyAction.TakeDamage` |

**13 个状态里，只有 8 个对应 Trigger。**

| | `EnemyStateType` | `EnemyAction` |
|---|---|---|
| 谁产生 | 行为树决策 | 状态内部 |
| 存哪 | **存进 `.asset`**（行为树节点） | **只在代码里传递** |
| 数量 | 13 | 8 |
| 含"不播动画"的项 | ✅（Idle / Chase） | ❌ |
| 含 Bool 型 | ✅（Dead / Dash / Stance） | ❌ |
| 序列化风险 | ⚠️ 有（改顺序会错位） | ✅ 无 |

**所以：**

- `EnemyStateType` 是**决策层的输出**，要落盘，所以它对枚举顺序敏感（阶段 4 会强调"只能往后加"）
- `EnemyAction` 是**表现层的指令**，只在内存里传递，随便改

**两者的数量不一样是常态**：一个状态可以播 0 个动作（Idle），
也可以播多个动作（未来做连段时，`AttackMelee` 里可能连续发三次 `Melee`）。

> **判断依据**：**如果一个枚举会存进资产，就对顺序敏感；如果只在代码里传，就随便改。**
> 这两类不要混用。

**规则 5：一个参数只表达一件事**

```
❌ AttackType（0=近战 1=远程 2=施法）  ← 一个参数挤了三种语义，Trigger 也做不到
✅ Melee / RangedAttack / Spell         ← 三个独立 Trigger
```
**规则 5：一个参数只表达一件事**

```
❌ AttackType（0=近战 1=远程 2=施法）  ← 一个参数挤了三种语义，Trigger 也做不到
✅ Melee / RangedAttack / Spell         ← 三个独立 Trigger
```

| # | 改哪 | 怎么改 |

| 1 | **Parameters 面板** | 双击名字，直接改。**注意：改完所有引用它的过渡条件会自动更新** |

| `_castSpellTrigger` | `"CastSpell"` | `"Spell"` |
| `_rollTrigger` | `"Roll"` | `"Dash"` |
| `_isHiddenParameter` | `"IsHidden"` | `"Stance"` |
| `_takeDamageTrigger` | `"TakeDamage"` | 不变 |
| `_isDeadParameter` | `"IsDead"` | 不变 |

> **为什么不在 Inspector 里改而改代码默认值**：
> Inspector 里改的值会覆盖代码默认值，但 prefab 一旦重建就丢了。

# 阶段 1：设计 Werewolf 的 Animator 状态机

## 目标

一个能手动控制的 `Werewolf_AI.controller`：11 个参数、10 个状态、17 条过渡。
在 Animator 窗口里手动拖参数，每个动作都能正确播放，任意动作能被任意动作打断，
而且**用两个 Float 就能同时表达"跑多快"和"往哪转"**。

**这一步不写代码。** 但它是整个流程里最容易卡住的一步——不是难，是坑多且都不报错。

## 为什么这一步最难

因为**动画和代码之间只有"参数名"这一根线**。

代码写 `SetTrigger("Melee")`，控制器里必须有叫 `Melee` 的 Trigger。
  
名字差一个字母，Unity **只打一条警告，不报错，动画就是不播**。

所以这一步必须一次做对，后面才不会怀疑代码。

## 步骤 1.1：盘点 Werewolf 的 22 个动画

### 为什么排除这 8 个（这是必须讲清的判断）

**`W Root` = 带根位移（Root Motion）的版本。**

这类动画会让角色**自己往前走**（位移写在动画里）。而我们的框架是：

```
CustomNavAgent（代码）负责移动  ←→  动画只负责"表现"
```

如果用了 `W Root` 版本，会变成**两套系统同时推角色**：

- 代码推一次
- 动画再推一次
- 结果：移动速度变成两倍、贴墙时抽搐、寻路完全失控

**所以必须用 `In Place` 版本**（原地动画），让代码独占移动权。

**`Jump In Place` 为什么也不用**：它是原地起跳，没有位移也没有攻击判定。
放进状态机只会让怪物无故弹跳。而且 `Jump Forward In Place` 已经覆盖了"跳"这个动作。

**`Turn Left` / `Turn Right` 为什么也不用**：

**转向由 `CustomNavAgent.turnSpeed` 负责，不由动画表现。**

```
ChaseState → Agent.SetDestination(目标) → Agent 按 turnSpeed 旋转 transform.forward
```

动画只负责"跑"，不需要知道"往哪转"。
"背对着挥爪"的风险由 `AttackState.OnEnter` 里的 `FaceTowards`（瞬时转向）解决。

### 排除的 8 个动画，分三类原因

| 类别 | 动画 | 为什么排除 |
|---|---|---|
| **技术重复** | 5 个 `W Root` | 同一动作的带位移版，会和代码抢移动权 |
| **无战斗语义** | `Jump In Place` | 原地跳，不构成任何战斗行为 |
| **职责错配** | `Turn Left` / `Turn Right` | 转向归寻路系统，不归动画系统 |

> **这就是"必须用上全部动作"的正确理解**：
>
> 不是机械地把 22 个动画全塞进状态机，而是**每个有战斗语义的动作都要有归属**。
>
> **能说出"为什么不用"，比"全都用上"更能说明你理解了。**
>
> 顺带一提：阶段 0 把 Shell 的 `Roll` 改名成 `Dash`、`IsHidden` 改名成 `Stance`，
> 用的是同一个思路——**把一个具体招式归到一个通用类别里**。
> 动画是这样，参数名也是这样。

## 步骤 1.6：转向怎么处理（不进动画系统）

### 一句话：转向完全交给 `CustomNavAgent`

**Animator 里没有任何东西负责转向。** 代码也不设任何转向参数。

转向的完整链路：

```
ChaseState.OnUpdate
  → Agent.SetDestination(目标位置)
      → Agent 内部按 turnSpeed 计算目标朝向
      → Rigidbody 旋转 transform.forward
  → Animator 只收到 SetMoveSpeed(0~1)
```

**所以"背对着挥爪"这个问题怎么解决？**

靠 `AttackState.OnEnter` 里的一行：

```csharp
if (Context.Target != null)
    Context.Agent.FaceTowards(Context.Target.position);
```

`FaceTowards` 是瞬时转向——在攻击判定之前把朝向摆正。
所以判定框永远在怪物的正前方，不会打空。

### 三种"转向场景"分别怎么处理

| 场景 | 谁负责 | 怎么做 |
|---|---|---|
| **追击时跟着玩家转** | `CustomNavAgent` | `SetDestination` 每帧刷新，Agent 按 `turnSpeed` 平滑转 |
| **攻击前正对目标** | `AttackState` | `FaceTowards` 瞬时转向（一行代码） |
| **目标在身后想先转身** | **不需要处理** | 追击时 Agent 已经在转了；攻击时 `FaceTowards` 会瞬间摆正 |

**第三种情况为什么不需要专门处理**：

因为 `FaceTowards` 是**瞬时**的。如果延迟 0.2 秒攻击，玩家可能在这 0.2 秒里移开，
反而更容易打空。**瞬时转向 + 立即攻击**是更可靠的做法。

### 这个决定省掉了什么

| 项 | 有 Turning | 无 Turning（现在） |
|---|---|---|
| Animator 参数 | 11 个（含 Turning） | **10 个** |
| Locomotion BlendTree | 2D，5 个 Motion | **1D，3 个 Motion** |
| BlendTree 坐标调试 | 要摆 5 个点 | 直线排 3 个 |
| 代码状态 | 6 个新增 | **5 个**（无 TurnToTarget） |
| 配置字段 | 8 个新增 | **7 个**（无 turnDuration） |
| 条件 | 7 个新增 | **6 个**（无 TargetBehind） |
| "转身不同步"问题 | 要专门处理 | **不存在** |

**一行 `FaceTowards` 顶掉了一整套 2D 混合设计。** 这就是"用对系统"的价值。

## 步骤 1.7：过渡设计（本阶段最重要的一节）

### 设计原则：AnyState 管"打断"，Exit Time 管"回去"

| 谁 | 管什么 |
|---|---|
| **AnyState** | **进入**任何动作。任何时候都能被任何动作打断 |
| **动作状态自己的 Exit Time** | **离开**。播完自动回 Locomotion |

好处：

- 动作之间**不需要互相连**（不用 O(n²)）
- 任意状态能被任意动作打断，天然成立
- 和代码状态机语义**完全一致**：`EnemyBrain.ChangeState` 也是无条件抢占

### 第一步：连 9 条 AnyState 过渡

选中 Animator 窗口左上角的 **AnyState** 节点 → Inspector → `+` → 拖到目标状态。

**每条都必须设这 3 项**：

| 设置项 | 值 | 为什么 |
|---|---|---|
| `Has Exit Time` | ❌ **取消勾选** | 勾了会"等当前动作播完才响应"，打断就失效 |
| `Transition Duration` | `0` | 有混合时间会让两个动作叠在一起，起始画面糊 |
| `Can Transition To Self` | ❌ **取消勾选** | 否则会自己打断自己（见坑 1） |

**9 条过渡表**：

| # | 目标状态 | 条件（每条只加 1 个条件） |
|---|---|---|
| 1 | `Alert` | `Alert` |
| 2 | `MeleeCombo` | `Melee` |
| 3 | `Smash` | `Heavy` |
| 4 | `Pounce` | `Pounce` |
| 5 | `Leap` | `Leap` |
| 6 | `RangedAttack` | `RangedAttack` |
| 7 | `CastSpell` | `Spell` |
| 8 | `TakeDamage` | `TakeDamage` |
| 9 | `Death` | `IsDead`（Bool，勾选 true 那个状态） |

> **顺序就是优先级，越靠下优先级越高。**
> 所以 `Death` **必须放最后一条**——死亡要压过受击。
> `TakeDamage` 放倒数第二条——受击要压过所有攻击动作。
> 其余攻击动作之间顺序无所谓，因为**代码一次只发一个 Trigger**。

### 第二步：连 8 条"回 Locomotion"

除 `Death` 外，每个动作状态都要有一条回 `Locomotion` 的过渡。

**选中动作状态 → Inspector → `+` → 拖到 Locomotion**

| From | Has Exit Time | Exit Time | Duration | 条件 |
|---|---|---|---|---|
| `Alert` | ✅ 勾选 | `0.9` | `0.1` | 无 |
| `MeleeCombo` | ✅ 勾选 | `0.9` | `0.1` | 无 |
| `Smash` | ✅ 勾选 | `0.9` | `0.1` | 无 |
| `Pounce` | ✅ 勾选 | `0.9` | `0.1` | 无 |
| `Leap` | ✅ 勾选 | `0.9` | `0.1` | 无 |
| `RangedAttack` | ✅ 勾选 | `0.9` | `0.1` | 无 |
| `CastSpell` | ✅ 勾选 | `0.9` | `0.1` | 无 |
| `TakeDamage` | ✅ 勾选 | `0.9` | `0.1` | 无 |

> **`Death` 不要连任何出口**。这是"死亡不可逆"在动画层的实现。

### 为什么没有任何一条过渡用 `MoveSpeed` 做条件

因为 `MoveSpeed` **只负责混合动画，不负责切换状态**。

`MoveSpeed` 从 0 变到 1 时，Locomotion 内部自动从 Idle 混合到 Run，**不需要状态切换**。

> **这一点直接解决了"Float 参数做过渡条件很麻烦"的困扰**：
> 只要不用 Float 做过渡条件，就不需要 Greater / Less / Equals 的任何组合。
>
> 分工是：**代码决定"什么时候进、什么时候出"，Animator 只负责"在状态内部怎么混合"。**

### 四个必须知道的坑

#### 坑 1：`Can Transition To Self` 必须取消

`MeleeCombo` 正在播第 2 段（左斩）时，如果 AnyState → `MeleeCombo` 的条件还成立，
会**从第 2 段跳回第 1 段**，动作卡在开头反复播。

Trigger 是消费型的（过渡用掉就清零），理论上不会重复触发。
但保险起见全部取消——成本为零，杜绝一类诡异 bug。

#### 坑 2：Trigger 用在 AnyState 上是安全的，Bool 要小心

| 类型 | 用在 AnyState | 原因 |
|---|---|---|
| **Trigger** | ✅ 安全 | 过渡被采用时自动清零，不会持续满足 |
| **Bool** | ⚠️ 小心 | 置 true 后一直满足，会持续打断 |
| **Float** | ⚠️ 小心 | 同上 |

本例唯一用 Bool 的是 `IsDead`，它指向 `Death` 而 `Death` 没有出口，
所以"持续满足"反而是正确行为（死了就一直死着）。

**如果哪天想用 Bool 做攻击**（如 `IsAttacking = true`），必须配"何时置回 false"的机制，
否则怪物卡在攻击状态里出不来。**这就是契约"一次性动作必须用 Trigger"的底层原因。**

#### 坑 3：`Death` 的过渡不能勾 Exit Time

勾了的话，血归零后要**等当前动作播完**才倒地。
如果它正在播 1.2 秒的施法，你会看到"血条空了，狼人还在优雅地施法"。

#### 坑 4：AnyState 进入式过渡一律 `Duration = 0`

有混合期的话，混合期间再来一个 Trigger，会出现"两段动画叠加"，动作糊成一团。

### 连完后的核对清单

```
Locomotion（默认状态，1D BlendTree，3 个 Motion）
  └ 内部混合，无过渡

AnyState 出发：9 条
  Alert / MeleeCombo / Smash / Pounce / Leap / RangedAttack / CastSpell / TakeDamage / Death

动作回 Locomotion：8 条
  Alert / MeleeCombo / Smash / Pounce / Leap / RangedAttack / CastSpell / TakeDamage

Death 出口：0 条
总计：17 条
```

# 阶段 2：重写接口（8 个方法 → 4 个）

## 目标

`IEnemyAnimator` 从 8 个方法收敛到 **4 个**，**里面不再出现任何怪物专属的名字**。
`NullEnemyAnimator` 和 `ShellAnimator` 跟着改，编译通过且 Shell 行为不变。

## 现在的接口有什么问题

```csharp
public interface IEnemyAnimator
{
    void SetMoveSpeed(float speed);   // ✅ 通用
    void PlayAttack();                // ❌ 写死"一种近战"
    void PlayRangedAttack();          // ❌ 写死"一种远程"
    void SetRoll(bool roll);          // ❌ Roll 是螃蟹的招式名
    void SetHidden(bool hidden);      // ❌ 缩壳是螃蟹的专属能力
    void PlayTakeDamage();            // ✅ 通用
    void SetDead(bool dead);          // ✅ 通用
}
```

**三个具体问题**：

**问题 1：`SetRoll` / `SetHidden` 是招式名，不是动作类别**

接口里出现这两个方法，等于宣布"**所有怪都必须有滚动和缩壳能力**"。

狼人没有缩壳，它只能写一个空方法：

```csharp
public void SetHidden(bool hidden) { }   // 狼人：空实现
```

**接口强迫所有怪物承认一个它们没有的能力**——这是设计错误。

**问题 2：`PlayAttack` 只有一种近战**

狼人有 4 种近战（咬/左斩/右斩/重击）。接口给一个 `PlayAttack()`，装不下。

**问题 3：命名契约没有落地**

阶段 0 定的契约里，参数叫 `Dash` / `Stance`，
但接口里叫 `SetRoll` / `SetHidden`。

**契约和代码对不上，契约就只是一张纸。**

## 新接口：4 个方法

```csharp
public interface IEnemyAnimator
{
    /// <summary>移动强度。0 = 待机，1 = 全速跑。</summary>
    void SetMoveSpeed(float normalizedSpeed);

    /// <summary>播放一次性动作。</summary>
    void PlayAction(EnemyAction action);

    /// <summary>开关可逆持续状态。</summary>
    void SetState(EnemyStateFlag state, bool active);

    /// <summary>死亡。只能置 true。</summary>
    void SetDead(bool dead);
}
```

> **参数用枚举，不用 string**。理由见阶段 0 规则 4——
> 字符串拼错编译通过、运行时静默忽略，是最难排查的一类 bug。
> 而这两个枚举只在代码内部传递，不进资产，所以用枚举没有任何序列化风险。

**4 个方法覆盖 12 个参数**：

| 方法 | 覆盖的参数 | 机制 |
|---|---|---|
| `SetMoveSpeed` | `MoveSpeed` | Float 直接赋值 |
| `PlayAction` | `Melee` / `Heavy` / `Pounce` / `Leap` / `RangedAttack` / `Spell` / `Alert` / `TakeDamage` | 8 个 Trigger，按 id 查 |
| `SetState` | `Dash` / `Stance` | 2 个 Bool，按 id 查 |
| `SetDead` | `IsDead` | Bool，只置 true |

### 为什么这 4 个方法就够了

因为**所有动作都能归进这四类**：

| 分类依据 | 例子 | 用哪个方法 |
|---|---|---|
| 连续变化的量 | 移动速度 | `SetMoveSpeed` |
| 播一次就结束 | 攻击、受击、施法、警戒 | `PlayAction(id)` |
| 能开能关的持续状态 | 冲刺、姿态 | `SetState(id, bool)` |
| 锁死到结束 | 死亡 | `SetDead` |

**新增一种怪，只要它的动作能归进这四类，接口就不用改。**

加第 3 只怪（比如"会钻地的沙虫"）：
- 钻地移动 → `EnemyStateFlag` 加一个 `Burrow`，**接口不变**
- 喷毒 → 复用 `EnemyAction.Ranged`，**接口不变**

### 2.1.2 重写接口

文件：`Assets/Scripts/AI/Enemy/EnemyAnimator/IEnemyAnimator.cs`

**整体替换**：

```csharp
namespace Emberwild.AI.Enemy.EnemyAnimator
{
    /// <summary>
    /// 怪物动画统一接口：状态类只依赖语义动作，各怪物自行翻译成自己的 Animator 参数。
    ///
    /// 【设计原则：接口里不许出现任何怪物或招式名】
    ///
    /// 判断一个方法该不该进这个接口，只问一句：
    ///   "换个完全不同的怪物，这个方法还有意义吗？"
    ///
    ///   SetMoveSpeed(float)              → 有意义（任何怪都要动）        → 进
    ///   PlayAction(EnemyAction)          → 有意义（任何怪都可能打人）    → 进
    ///   SetState(EnemyStateFlag, bool)   → 有意义（冲刺/姿态是通用类别） → 进
    ///   SetDead(bool)                    → 有意义（任何怪都会死）        → 进
    ///
    ///   SetRoll(bool)      → 没意义（Roll 是螃蟹的招式名）    → 删
    ///   SetHidden(bool)    → 没意义（缩壳是螃蟹的专属）      → 删
    ///   PlayRangedAttack() → 没意义（远近差别在参数表里）    → 删，用 PlayAction(EnemyAction.Ranged)
    ///
    /// 只有 4 个方法，意味着新增怪物只需要"配参数 + 配映射"，
    /// 不需要为它新写一个实现类。
    ///
    /// 【为什么用枚举而不是 string】
    ///   字符串 actionId 拼错时编译通过、运行时静默忽略——这是最难排查的一类 bug。
    ///   枚举让拼写错误变成编译错误。
    ///   本接口的参数只在代码内部传递，不涉及资产序列化，所以用枚举没有风险。
    ///
    /// 【参数名契约】（阶段 0 定义，阶段 3 在映射表里落地）
    ///   MoveSpeed                                         Float
    ///   Melee / Heavy / Pounce / Leap
    ///   RangedAttack / Spell / Alert / TakeDamage         Trigger
    ///   Dash / Stance                                     Bool
    ///   IsDead                                            Bool
    /// </summary>
    public interface IEnemyAnimator
    {
        /// <summary>
        /// 移动表现强度。0 = 待机，1 = 全速跑。驱动 Locomotion 的 BlendTree。
        ///
        /// ⚠️ 用比例而不是米/秒：不同怪速度差很大（3~8 米/秒），
        ///    用绝对值会让 BlendTree 的阈值无法跨怪统一。
        /// </summary>
        void SetMoveSpeed(float normalizedSpeed);

        /// <summary>
        /// 播放一次性动作（Animator Trigger）。
        ///
        /// 实现方若没有这个能力，应当静默忽略（不报错、不播），
        /// 避免因某个怪的招式缺失而中断整个 AI。
        ///
        /// 传什么都不会"拼错"——这是枚举相对字符串最大的价值。
        /// </summary>
        void PlayAction(EnemyAction action);

        /// <summary>
        /// 开关可逆持续状态（Animator Bool）。
        ///
        /// 为什么是 Bool 而不是 Trigger：这些状态需要能"主动结束"，
        /// Trigger 播完自动清零，没有"关闭"的语义。
        /// </summary>
        void SetState(EnemyStateFlag state, bool active);

        /// <summary>
        /// 死亡。**只能置 true**。
        ///
        /// 为什么单独一个方法而不并进 SetState：
        ///   死亡不可逆。如果写成 SetState(EnemyStateFlag.Dead, false)，
        ///   会让人以为可以复活，但框架并没有实现复活逻辑。
        ///   独立方法签名本身就表达了"这个不该传 false"。
        /// </summary>
        void SetDead(bool dead);
    }
}
```

|---|---|---|
| 方法数 | 8 | **4** |
| `PlayAction` 参数 | `string actionId` | **`EnemyAction action`** |
| `SetState` 参数 | `string stateId` | **`EnemyStateFlag state`** |
| 删掉的方法 | — | `PlayAttack` / `PlayRangedAttack` / `SetRoll` / `SetHidden` / `PlayTakeDamage` |

### 3.2 加 4 个新方法（在类末尾）

```csharp
        // ═══════════════════════════════════════════════════════════
        // IEnemyAnimator 的 4 个方法（新接口，参数用枚举）
        // ═══════════════════════════════════════════════════════════

        public void SetMoveSpeed(float normalizedSpeed)
        {
            if (_animator == null) return;
            _animator.SetFloat(_speedHash, Mathf.Clamp01(normalizedSpeed));
        }

        /// <summary>
        /// 按动作枚举播放。
        ///
        /// Shell 只有 Melee / Ranged / Spell / TakeDamage 四种。
        /// 其余四种（Heavy / Pounce / Leap / Alert）它没有，静默忽略。
        ///
        /// 为什么静默忽略而不是"退化成近战"：
        ///   退化成近战会让行为树配错时"看起来能用"，反而更难排查。
        ///   静默忽略配合阶段 3 的"能力清单日志"，能立刻看出这只怪缺什么。
        /// </summary>
        public void PlayAction(EnemyAction action)
        {
            if (_animator == null) return;

            switch (action)
            {
                case EnemyAction.Melee:
                    Trigger(_attackHash);
                    break;

                case EnemyAction.Ranged:
                    Trigger(_projectileAttackHash);
                    break;

                case EnemyAction.Spell:
                    Trigger(_castSpellHash);
                    break;

                case EnemyAction.TakeDamage:
                    Trigger(_takeDamageHash);
                    break;

                // Shell 没有这四种能力，静默忽略
                case EnemyAction.Heavy:
                case EnemyAction.Pounce:
                case EnemyAction.Leap:
                case EnemyAction.Alert:
                    break;
            }
        }

        /// <summary>开关可逆状态。Shell 只有 Dash（滚动）和 Stance（缩壳）。</summary>
        public void SetState(EnemyStateFlag state, bool active)
        {
            if (_animator == null) return;

            switch (state)
            {
                case EnemyStateFlag.Dash:
                    _animator.SetBool(_rollHash, active);
                    break;

                case EnemyStateFlag.Stance:
                    _animator.SetBool(_isHiddenHash, active);
                    break;
            }
        }

        public void SetDead(bool dead)
        {
            if (_animator == null) return;
            _animator.SetBool(_isDeadHash, dead);
        }

        /// <summary>
        /// 触发一个 Trigger。
        ///
        /// 单独抽成方法的原因：所有动作都要做"先 Reset 再 Set"，
        /// 重复四次不如抽一次。而且这个"Reset 再 Set"的理由值得集中写一遍：
        ///
        /// Trigger 是消费型的——过渡用了就自动清零。
        /// 如果同一帧内连续两次 SetTrigger，第二次不会产生新的上升沿，动画就漏播了。
        /// Reset 保证每次调用都产生一次完整事件。
        /// </summary>
        private void Trigger(int hash)
        {
            if (hash == 0) return;
            _animator.ResetTrigger(hash);
            _animator.SetTrigger(hash);
        }
```

```csharp
        public void SetRoll(bool roll) { ... }
        public void SetHidden(bool hidden) { ... }
        public void PlayTakeDamage() { ... }
```

>

### 3.4 为什么这个 switch 不用写 default

看 `PlayAction` 的 `switch`：

```csharp
switch (action)
{
    case EnemyAction.Melee:      ...
    case EnemyAction.Heavy:      break;
    case EnemyAction.Pounce:     break;
    case EnemyAction.Leap:       break;
    case EnemyAction.Ranged:     ...
    case EnemyAction.Spell:      ...
    case EnemyAction.Alert:      break;
    case EnemyAction.TakeDamage: ...
}
```

**8 个枚举值全部列出来了，所以不需要 `default`。**

这就是枚举相对字符串的另一个好处：

| | 字符串 switch | 枚举 switch |
|---|---|---|
| 漏掉一个值 | 不报错，运行时静默走 default | **编译器警告 CS8509**（switch expression）或 IDE 提示未覆盖 |
| 新增一个值 | 完全不知道哪里要改 | **IDE 会标出所有未覆盖的 switch** |

**实操建议**：写 `switch` 时**刻意不写 `default`**，
这样新增枚举值时编译器会提醒你"这里没覆盖"。
如果写了 `default: break;`，新增值会静默走进 default，回到字符串时代的问题。

> ⚠️ 唯一例外：如果你**故意**想让某些值"什么都不做"（比如 Shell 没有那四个动作），
> 那就显式列出 `case ...: break;`——**显式表示"我知道这个值，选择不做"**。
> 这和"忘了写"是两回事。

# 阶段 3：写通用实现类（一个类服务所有怪）

## 目标

新建 **一个** `EnemyAnimator` 类，替代 `ShellAnimator` + 未来要写的 `WerewolfAnimator`。

Console 能看到参数校验结果，Shell 和 Werewolf 共用同一个类。

## 为什么这次只要一个类

前几版手册里，我打算写 `WerewolfAnimator`（第二只怪一个类）。
但阶段 0、阶段 2 做完之后，**情况变了**：

| 项 | 改造前 | 改造后 |
|---|---|---|
| Shell 参数名 | `Speed` / `Attack` / `Roll` / `IsHidden` … | `MoveSpeed` / `Melee` / `Dash` / `Stance` … |
| Werewolf 参数名 | — | `MoveSpeed` / `Melee` / `Dash` … |
| 两者是否一致 | ❌ 完全不同 | ✅ **完全一致** |

**参数名统一后，"为每只怪写一个类"就失去了理由。**

因为两个类的差异只在于：
1. 参数名字符串不同 → 现在相同了
2. 有的怪没有某个能力 → 用"启动时检测参数是否存在"解决

### 这解决了什么问题

| 问题 | 改造前 | 改造后 |
|---|---|---|
| 新增怪物要写新类 | 是（每个怪一个 200 行） | **否**（0 行） |
| 改一个 bug 要改 N 处 | 是 | **否**（只有一处） |
| 参数字符串散落各处 | 是（每类 10 个字段） | **否**（集中在一张表） |

**这才是"命名契约"的真正收益。**

> 注意：这不是"提前抽象"。
> 而是**已经看到两个类会 90% 重复之后，消除重复**。
> 阶段 8 会讨论"什么时候该抽象"和"这次为什么可以"。

## 步骤 3.1：新建 `EnemyAnimator.cs`

文件：`Assets/Scripts/AI/Enemy/EnemyAnimator/EnemyAnimator.cs`

```csharp
using System.Collections.Generic;
using Emberwild.Core.AppLog;
using UnityEngine;

namespace Emberwild.AI.Enemy.EnemyAnimator
{
    /// <summary>
    /// 通用动画驱动：一个类服务所有怪物。
    ///
    /// 【为什么只有一个实现类】
    /// 因为所有怪物的 Animator 参数名都遵循【参数命名契约】（阶段 0）。
    /// 参数名统一后，实现类的唯一差异就消失了——
    /// 剩下的只有"这只怪有没有某个参数"，用启动时检测解决。
    ///
    /// 【怎么新增一只怪】
    /// 1. 控制器里按契约命名参数
    /// 2. 挂这个组件
    /// 3. 完事——不需要写任何 C# 代码
    ///
    /// 【契约表在这里落地】
    /// 下面两个数组就是契约的代码化表达。
    /// 改这里 = 改契约，所有怪跟着生效。
    /// </summary>
    [DisallowMultipleComponent]
    public class EnemyAnimator : MonoBehaviour, IEnemyAnimator
    {
        [Tooltip("怪物 Animator；留空自动在子物体里查找")]
        [SerializeField] private Animator _animator;

        [Header("参数校验")]
        [Tooltip("启动时检查必需参数是否存在，缺失会打警告")]
        [SerializeField] private bool _validateOnAwake = true;

        // ═══════════════════════════════════════════════════════════
        // 契约表（代码化）
        //
        // 【为什么用数组 + 枚举索引，而不是 Dictionary<枚举, string>】
        //   枚举是连续整数（0..N），可以直接当数组下标。
        //   数组访问 O(1) 且没有装箱，Dictionary 有哈希开销。
        //   而且数组长度和枚举值数量的一致性可以在启动时断言，
        //   漏写一个会被立刻发现（Dictionary 不会）。
        //
        // 【代价】数组顺序必须与枚举声明顺序严格一致。
        //   所以下面每个元素都写了注释标注它对应哪个枚举值。
        //   改枚举顺序必须同步改这里——用 Count 断言兜底。
        // ═══════════════════════════════════════════════════════════

        /// <summary>
        /// EnemyAction → Animator Trigger 参数名。
        /// **下标必须与 EnemyAction 的声明顺序一一对应。**
        /// </summary>
        private static readonly string[] ActionParameters =
        {
            "Melee",        // EnemyAction.Melee      = 0
            "Heavy",        // EnemyAction.Heavy      = 1
            "Pounce",       // EnemyAction.Pounce     = 2
            "Leap",         // EnemyAction.Leap       = 3
            "RangedAttack", // EnemyAction.Ranged     = 4
            "Spell",        // EnemyAction.Spell      = 5
            "Alert",        // EnemyAction.Alert      = 6
            "TakeDamage",   // EnemyAction.TakeDamage = 7
        };

        /// <summary>
        /// EnemyStateFlag → Animator Bool 参数名。
        /// **下标必须与 EnemyStateFlag 的声明顺序一一对应。**
        /// </summary>
        private static readonly string[] StateParameters =
        {
            "Dash",     // EnemyStateFlag.Dash   = 0
            "Stance",   // EnemyStateFlag.Stance = 1
        };

        /// <summary>移动强度参数名。所有怪都必须有。</summary>
        private const string MoveSpeedParameter = "MoveSpeed";

        /// <summary>死亡参数名。所有怪都必须有。</summary>
        private const string DeadParameter = "IsDead";

        // ─────────── 运行时缓存 ───────────

        private int _moveSpeedHash;
        private int _deadHash;

        /// <summary>
        /// 动作 hash 缓存。下标 = (int)EnemyAction。
        /// 用数组而不是 Dictionary，理由同上。
        /// 值为 0 表示"这个动作对应的参数不存在"（已查过一遍）。
        /// </summary>
        private int[] _actionHashes;

        private int[] _stateHashes;

        /// <summary>这个控制器里实际存在的参数名集合。</summary>
        private readonly HashSet<string> _available = new HashSet<string>();

        private void Awake()
        {
            if (_animator == null) _animator = GetComponentInChildren<Animator>(true);

            if (_animator == null)
            {
                // 不是 Error：没动画的怪也能跑 AI，只是一直不动
                AppLog.Warning("Enemy", name + "：找不到 Animator，所有动画调用将被忽略");
                return;
            }

            // 断言：数组长度必须和枚举值数量一致，防止漏写
            AssertContractSize();

            _moveSpeedHash = Animator.StringToHash(MoveSpeedParameter);
            _deadHash = Animator.StringToHash(DeadParameter);

            _actionHashes = new int[ActionParameters.Length];
            _stateHashes = new int[StateParameters.Length];

            CollectAvailableParameters();

            if (_validateOnAwake) ValidateContract();
        }

        /// <summary>
        /// 检查映射表长度是否等于枚举值数量。
        ///
        /// 这个断言是本设计的安全网：
        /// 如果将来给 EnemyAction 加了一个值但忘了在 ActionParameters 加一行，
        /// 这里会立刻报错，而不是运行时数组越界（IndexOutOfRangeException）。
        ///
        /// 用数组索引换性能的代价，就是必须自己维护"长度一致"这个不变式。
        /// </summary>
        private static void AssertContractSize()
        {
            int actionCount = System.Enum.GetValues(typeof(EnemyAction)).Length;
            int stateCount = System.Enum.GetValues(typeof(EnemyStateFlag)).Length;

            if (ActionParameters.Length != actionCount)
            {
                AppLog.Error("Enemy",
                    "契约表不一致：EnemyAction 有 " + actionCount + " 个值，"
                    + "但 ActionParameters 有 " + ActionParameters.Length + " 项。"
                    + "给枚举加值后必须同步加映射表项。");
            }

            if (StateParameters.Length != stateCount)
            {
                AppLog.Error("Enemy",
                    "契约表不一致：EnemyStateFlag 有 " + stateCount + " 个值，"
                    + "但 StateParameters 有 " + StateParameters.Length + " 项。");
            }
        }

        /// <summary>收集控制器里实际有哪些参数。</summary>
        private void CollectAvailableParameters()
        {
            _available.Clear();
            if (_animator == null) return;

            AnimatorControllerParameter[] ps = _animator.parameters;
            for (int i = 0; i < ps.Length; i++) _available.Add(ps[i].name);
        }

        /// <summary>
        /// 启动时检查契约，并打印"这只怪有哪些能力"。
        ///
        /// 分两级：
        ///   缺失 MoveSpeed / IsDead → Warning（所有怪都该有）
        ///   缺失某个动作/状态参数   → **不警告**（说明这只怪没这个能力，正常）
        ///
        /// 所以不要把"缺 Heavy"当错误——狼人缺 Stance 是对的。
        /// </summary>
        private void ValidateContract()
        {
            if (_animator == null) return;

            if (!_available.Contains(MoveSpeedParameter))
                AppLog.Warning("Enemy", name + "：控制器缺少必需参数 'MoveSpeed'，移动动画不会生效");

            if (!_available.Contains(DeadParameter))
                AppLog.Warning("Enemy", name + "：控制器缺少必需参数 'IsDead'，死亡动画不会播");

            // 只列出"有"的能力，不抱怨"没有"的
            var actions = new List<string>();
            for (int i = 0; i < ActionParameters.Length; i++)
                if (_available.Contains(ActionParameters[i]))
                    actions.Add(((EnemyAction)i).ToString());

            var states = new List<string>();
            for (int i = 0; i < StateParameters.Length; i++)
                if (_available.Contains(StateParameters[i]))
                    states.Add(((EnemyStateFlag)i).ToString());

            AppLog.Info("Enemy", name + "：动画契约就绪。动作 [" + string.Join(", ", actions)
                + "]  状态 [" + string.Join(", ", states) + "]");
        }

        // ═══════════════════════════════════════════════════════════
        // IEnemyAnimator 实现
        // ═══════════════════════════════════════════════════════════

        public void SetMoveSpeed(float normalizedSpeed)
        {
            if (_animator == null) return;
            if (!_available.Contains(MoveSpeedParameter)) return;

            _animator.SetFloat(_moveSpeedHash, Mathf.Clamp01(normalizedSpeed));
        }

        public void PlayAction(EnemyAction action)
        {
            if (_animator == null) return;

            int index = (int)action;

            // 防御性边界检查：正常情况下枚举值与数组长度一致（Awake 已断言），
            // 但如果运行期有人用反射塞了非法值，这里兜住，不让它变成数组越界
            if (index < 0 || index >= ActionParameters.Length) return;

            string parameterName = ActionParameters[index];

            // 契约里有，但这个怪没有这个能力 → 正常，静默跳过
            if (!_available.Contains(parameterName)) return;

            int hash = ResolveActionHash(index, parameterName);
            if (hash == 0) return;

            // 先 Reset 再 Set：Trigger 是消费型的，
            // 同一帧连续两次 SetTrigger 第二次不会产生上升沿，动画会漏播
            _animator.ResetTrigger(hash);
            _animator.SetTrigger(hash);
        }

        public void SetState(EnemyStateFlag state, bool active)
        {
            if (_animator == null) return;

            int index = (int)state;
            if (index < 0 || index >= StateParameters.Length) return;

            string parameterName = StateParameters[index];
            if (!_available.Contains(parameterName)) return;

            int hash = ResolveStateHash(index, parameterName);
            if (hash == 0) return;

            _animator.SetBool(hash, active);
        }

        public void SetDead(bool dead)
        {
            if (_animator == null) return;
            if (!_available.Contains(DeadParameter)) return;

            _animator.SetBool(_deadHash, dead);
        }

        // ─────────── hash 缓存 ───────────

        /// <summary>
        /// 解析动作 hash（带缓存）。
        ///
        /// 用数组下标缓存而不是 Dictionary：
        ///   SetMoveSpeed 每帧都调，PlayAction 也频繁，
        ///   数组访问比字典快且不产生装箱。
        /// </summary>
        private int ResolveActionHash(int index, string parameterName)
        {
            int hash = _actionHashes[index];
            if (hash != 0) return hash;

            hash = Animator.StringToHash(parameterName);
            _actionHashes[index] = hash;
            return hash;
        }

        private int ResolveStateHash(int index, string parameterName)
        {
            int hash = _stateHashes[index];
            if (hash != 0) return hash;

            hash = Animator.StringToHash(parameterName);
            _stateHashes[index] = hash;
            return hash;
        }

        // ═══════════════════════════════════════════════════════════
        // 调试：Inspector 里右键组件可直接测试
        // ═══════════════════════════════════════════════════════════

        [ContextMenu("测试：播放近战")]
        private void DebugMelee() { PlayAction(EnemyAction.Melee); }

        [ContextMenu("测试：播放受击")]
        private void DebugTakeDamage() { PlayAction(EnemyAction.TakeDamage); }

        [ContextMenu("测试：进入冲刺")]
        private void DebugDashOn() { SetState(EnemyStateFlag.Dash, true); }

        [ContextMenu("测试：退出冲刺")]
        private void DebugDashOff() { SetState(EnemyStateFlag.Dash, false); }

        [ContextMenu("测试：进入姿态")]
        private void DebugStanceOn() { SetState(EnemyStateFlag.Stance, true); }

        [ContextMenu("测试：退出姿态")]
        private void DebugStanceOff() { SetState(EnemyStateFlag.Stance, false); }
    }
}
```

### 关于"数组 + 枚举索引"这个选择的取舍

我用 `string[]` 而不是 `Dictionary<EnemyAction, string>`，理由是性能和"漏写能被断言发现"。

但**这个选择有代价**，必须说清楚：

| | `Dictionary<EnemyAction, string>` | `string[]` + 枚举索引（当前） |
|---|---|---|
| 查找速度 | 哈希，约 20~50ns | 数组，约 1~2ns |
| 顺序依赖 | ✅ 无（key 是枚举） | ❌ **必须与枚举声明顺序一致** |
| 漏写一项 | ❌ 运行时 KeyNotFound，不易发现 | ✅ **Awake 里长度断言立刻报错** |
| 可读性 | ✅ 直接写 `{ EnemyAction.Melee, "Melee" }` | ⚠️ 靠注释标注下标 |
| 装箱 | ❌ 会（枚举 key 装箱） | ✅ 不会 |

**为什么最终选数组**：

1. `SetMoveSpeed` 每帧调用，`PlayAction` 也很频繁。虽然 20ns 不算什么，但这是个可以零成本避免的开销
2. **漏写的检测更重要**。字典漏写一项，只会在这只怪第一次用那个动作时静默失败；
   数组漏写会被 `AssertContractSize()` 在 Awake 就抓住
3. 顺序依赖的风险被断言 + 逐行注释兜住了

> 如果你更看重可读性，换成 `Dictionary<EnemyAction, string>` 也完全可以。
> 那时把 `AssertContractSize()` 改成"检查字典 Count 是否等于枚举值数量"即可。
>
> **两种都能工作，区别只在"你更怕哪个问题"**：
> 怕性能 → 数组；怕顺序错 → 字典。
> 我选数组，是因为这个类的调用频率高，而顺序错有编译期看不出但运行期立刻报的兜底。

## 阶段 3 小结：这次改造到底省了什么

| 项 | 改造前（每怪一个类） | 改造后（一个类） |
|---|---|---|
| 新增怪物要写的 C# | ~200 行 | **0 行** |
| 参数名散落处 | 每个类 10 个字段 | **1 处数组** |
| 修一个动画 bug | 改 N 个类 | **改 1 处** |
| 新增一种动作 | 改 N 个类 + 接口 | **枚举加 1 值 + 数组加 1 项 + 编译器提醒所有 switch** |
| 排查"这个怪有哪些能力" | 翻代码 | **看 Console 一行日志** |
| 拼错动作名 | 运行时静默忽略 | **编译不过** |

**但要注意两个前提**：

1. **阶段 0 必须先把 Shell 参数名改成契约名**。否则一个类没法同时满足两套命名。
2. **枚举只用在"代码内部传递"，不落盘**。如果哪天要把 `EnemyAction` 存进资产，
   就必须接受"只能往后加值"的约束（像 `EnemyStateType` 那样）。

> **顺序很重要：先统一命名，再合并实现。**
> 反过来做不了。


```csharp
using UnityEngine;

namespace Emberwild.AI.Enemy.State
{
    // ═══════════════════════════════════════════════════════════
    // Werewolf 专属状态（6 个）
    //
    // 为什么放在一个文件：它们只服务一只怪，且彼此逻辑相似。
    // 如果哪天第 3 只怪也要用，应该拆成独立文件并考虑参数化——
    // 现在拆是过度设计。
    // ═══════════════════════════════════════════════════════════

    /// <summary>
    /// 警戒：刚发现目标时张望一下。
    ///
    /// 为什么需要：直接从 Idle 跳到 Chase 很突兀，玩家看不到"它发现我了"这个反馈。
    /// 播一次 Look Left Right，给玩家 0.8 秒的反应时间。
    /// </summary>
    public class AlertState : IEnemyState
    {
        private float _endTime;

        public void OnEnter(EnemyBrain brain)
        {
            brain.Agent.Stop();
            brain.Animator.SetMoveSpeed(0f);
            brain.Animator.PlayAction(EnemyAction.Alert);

            // 置一次性标志：这场战斗不再警戒
            brain.BB.HasAlerted = true;
            _endTime = Time.time + brain.AlertDuration;
        }

        public void OnUpdate(EnemyBrain brain)
        {
            if (Time.time >= _endTime)
            {
                brain.ChangeState(brain.BB.CanSeeTarget ? EnemyStateType.Chase : EnemyStateType.Idle);
            }
        }

        public void OnExit(EnemyBrain brain) { }
    }

    /// <summary>
    /// 重击：慢、伤害高。
    ///
    /// 和 AttackMeleeState 的差别：
    ///   1. 走 PlayAction(EnemyAction.Heavy) 而不是 EnemyAction.Melee
    ///   2. 硬直更长（用独立的配置项）
    ///   3. 记 LastHeavyTime 而不是 LastAttackTime（独立冷却）
    /// </summary>
    public class AttackHeavyState : IEnemyState
    {
        public void OnEnter(EnemyBrain brain)
        {
            brain.Agent.Stop();
            brain.Animator.SetMoveSpeed(0f);

            if (brain.BB.Target != null) brain.Agent.FaceTowards(brain.BB.Target.position);

            // 重击用独立窗口（更长），否则窗口按 attackDuration 算会提前解锁
            brain.Combat.DoAttack(EnemyAction.Heavy, brain.HeavyAttackDuration);
            brain.BB.LastHeavyTime = Time.time;
            brain.BB.LastAttackTime = Time.time;   // 重击也占用"总体攻击节奏"
        }

        public void OnUpdate(EnemyBrain brain)
        {
            if (!brain.Combat.IsAttacking)
            {
                brain.ChangeState(brain.BB.CanSeeTarget ? EnemyStateType.Chase : EnemyStateType.Idle);
            }
        }

        public void OnExit(EnemyBrain brain) { }
    }

    /// <summary>
    /// 扑击：中距离高速突进 + 一次攻击。
    ///
    /// 为什么不能复用 RollChaseState：
    ///   Roll 是"只位移不攻击"，扑击是"位移 + 攻击"。
    ///   而且 RollChase 用的是 brain.RollSpeed / RollDuration，
    ///   扑击要独立参数，否则调扑击距离会影响螃蟹的滚动。
    /// </summary>
    public class PounceState : IEnemyState
    {
        private Vector3 _direction;
        private float _endTime;

        public void OnEnter(EnemyBrain brain)
        {
            brain.Agent.Stop();
            brain.Animator.SetMoveSpeed(1f);       // 冲刺时用跑步动画
            brain.Animator.PlayAction(EnemyAction.Pounce);

            Vector3 dir = brain.BB.Target != null
                ? brain.BB.Target.position - brain.transform.position
                : brain.transform.forward;
            dir.y = 0f;
            _direction = dir.sqrMagnitude > 0.001f ? dir.normalized : brain.transform.forward;

            brain.BB.LastPounceTime = Time.time;
            brain.BB.LastAttackTime = Time.time;

            // 位移和攻击同时开始：伤害在 DoAttack 里立刻结算
            brain.Combat.DoAttack(EnemyAction.Pounce);
            _endTime = Time.time + brain.PounceDuration;
        }

        public void OnUpdate(EnemyBrain brain)
        {
            brain.Agent.SetDirectVelocity(_direction, brain.PounceSpeed);

            if (Time.time >= _endTime)
            {
                brain.ChangeState(brain.BB.CanSeeTarget ? EnemyStateType.Chase : EnemyStateType.Idle);
            }
        }

        public void OnExit(EnemyBrain brain)
        {
            brain.Agent.Stop();
            brain.Animator.SetMoveSpeed(0f);
        }
    }

    /// <summary>
    /// 跃击：远距离跳过去，位移更长更慢。
    ///
    /// 和 Pounce 的区别：Pounce 是"短促突进"，Leap 是"长距离跳跃"。
    /// 参数不同，逻辑相同——这正是"应该参数化"的信号（阶段 8 会讲）。
    /// </summary>
    public class LeapState : IEnemyState
    {
        private Vector3 _direction;
        private float _endTime;

        public void OnEnter(EnemyBrain brain)
        {
            brain.Agent.Stop();
            brain.Animator.SetMoveSpeed(1f);
            brain.Animator.PlayAction(EnemyAction.Leap);

            Vector3 dir = brain.BB.Target != null
                ? brain.BB.Target.position - brain.transform.position
                : brain.transform.forward;
            dir.y = 0f;
            _direction = dir.sqrMagnitude > 0.001f ? dir.normalized : brain.transform.forward;

            brain.BB.LastLeapTime = Time.time;
            brain.Combat.DoAttack(EnemyAction.Leap);
            _endTime = Time.time + brain.LeapDuration;
        }

        public void OnUpdate(EnemyBrain brain)
        {
            brain.Agent.SetDirectVelocity(_direction, brain.LeapSpeed);

            if (Time.time >= _endTime)
            {
                brain.ChangeState(brain.BB.CanSeeTarget ? EnemyStateType.Chase : EnemyStateType.Idle);
            }
        }

        public void OnExit(EnemyBrain brain)
        {
            brain.Agent.Stop();
            brain.Animator.SetMoveSpeed(0f);
        }
    }

    /// <summary>
    /// 施法：播一次 Cast Spell，期间不能动。
    ///
    /// 本阶段只做表现（播动画 + 站住），不接实际 Buff 效果。
    /// 为什么先不做效果：效果属于战斗系统，不是 AI 的职责。
    /// AI 只负责"什么时候施法"。
    /// </summary>
    public class CastSpellState : IEnemyState
    {
        private float _endTime;

        public void OnEnter(EnemyBrain brain)
        {
            brain.Agent.Stop();
            brain.Animator.SetMoveSpeed(0f);
            brain.Animator.PlayAction(EnemyAction.Spell);

            brain.BB.LastSpellTime = Time.time;
            _endTime = Time.time + brain.SpellDuration;
        }

        public void OnUpdate(EnemyBrain brain)
        {
            if (Time.time >= _endTime)
            {
                brain.ChangeState(brain.BB.CanSeeTarget ? EnemyStateType.Chase : EnemyStateType.Idle);
            }
        }

        public void OnExit(EnemyBrain brain) { }
    }
}
```

```csharp
        /// <summary>
        /// 发动一次攻击。
        /// </summary>
        /// <param name="action">
        /// 动作枚举。默认 <see cref="EnemyAction.Melee"/>，
        /// 这样 `AttackMeleeState` 里写 `DoAttack()` 仍能编译，
        /// 只有 Werewolf 的重击/扑击/跃击才传别的值。
        /// </param>
        /// <param name="duration">
        /// 攻击窗口时长（秒）。传 -1 或省略 = 用 EnemyAIConfig.attackDuration。
        /// 重击这类"慢招"需要更长的窗口，所以要能覆盖。
        /// </param>
        /// <returns>false = 正在攻击中，本次被忽略。</returns>
        public bool DoAttack(EnemyAction action = EnemyAction.Melee, float duration = -1f)
        {
            if (IsAttacking) return false;

            // duration <= 0 表示用配置里的默认攻击窗口
            float window = duration > 0f ? duration : _attackDuration;
            _attackEndTime = Time.time + window;

            // 统一走 PlayAction：接口里已经没有任何"具体招式"方法了
            Animator?.PlayAction(action);

            EventBus.Publish(new CharacterAttackHitEvent(_entity, ComboIndex));
            AppLog.Info("Combat", $"{name} 发起攻击 [{action}] 窗口={window}s");
            return true;
        }

        /// <summary>
        /// 发动一次远程攻击。
        /// </summary>
        /// <param name="targetPos">攻击目标点，作为判定中心。</param>
        /// <param name="action">动作枚举，默认 <see cref="EnemyAction.Ranged"/>。</param>
        /// <returns>false = 正在攻击中，本次被忽略。</returns>
        public bool DoRangedAttack(Vector3 targetPos, EnemyAction action = EnemyAction.Ranged)
        {
            if (IsAttacking) return false;

            _attackEndTime = Time.time + _attackDuration;

            Animator?.PlayAction(action);

            EventBus.Publish(new CharacterAttackHitEvent(_entity, 1, targetPos));
            AppLog.Info("Combat", $"{name} 发起远程攻击 [{action}] target={targetPos}");
            return true;
        }
```

### 为什么默认值用枚举而不是 null

之前写的是 `string actionId = null`，靠"null 表示用默认近战"。

改成枚举后，**默认值可以直接写成 `EnemyAction.Melee`**，比 null 清楚得多：

| | `string actionId = null` | `EnemyAction action = EnemyAction.Melee` |
|---|---|---|
| 调用方写 `DoAttack()` | 内部判断 `isNullOrEmpty` → 用 "melee" | 直接用枚举默认值 |
| 读懂默认行为 | 要翻实现 | **看签名就知道** |
| 传非法值 | 可能，运行时静默 | **不可能** |
| 多一次判空 | 要 | **不要** |

### 返回值从 void 改成 bool

顺手加了个 `return true/false`。

**为什么**：调用方（状态类）需要知道"这次攻击有没有真的发出去"。
`AttackState` 里原来是：

```csharp
brain.Combat.DoAttack(...);
// 然后不管成功与否都继续
```

改成：

```csharp
if (!brain.Combat.DoAttack(...))
{
    Finish();   // 没打出去，立刻结束状态，让行为树重新决策
    return;
}
```

**这样"因为还在攻击冷却中被忽略"就不会导致状态卡住**。

> 这是"顺手发现的小改进"，不在原计划里。
> 但它体现了读代码时的判断：**这个方法返回 void，调用方就永远不知道成功没成功。**

### 为什么 `attackDuration` 要和动画长度对齐

`attackDuration` 决定"攻击窗口"——窗口内怪物不能动、不能再次攻击。

如果把窗口设成 0.5 秒，但咬击动画有 0.8 秒，会发生：

```
0.0s  代码：开始攻击，播咬击
0.5s  代码：窗口结束 → 状态切到 Chase → 设 MoveSpeed = 1
0.8s  动画：咬击播完 → Animator 回 Locomotion
       ↑ 0.5~0.8 秒之间，狼人在"边滑行边播咬击"
```

视觉上是**攻击时往前滑一段**。这是新手最常见的"动作不干净"原因。

**怎么定这个值**：在 Animator 里点开 `MeleeCombo → Bite`，Inspector 会显示该状态的
Motion（`Bite Attack`），点一下能看动画长度（约 0.8 秒）。

**规则**：`attackDuration` ≈ 动画长度 × 0.85

**Shell 为什么不明显**：螃蟹咬击动画短（约 0.6 秒），`attackDuration` 也是 0.6，碰巧对上了。

> 这就是"配置项之间存在隐式耦合"——`attackDuration` 和动画长度没有任何代码关联，
> 只能靠人对齐。**第 3、4 只怪会遇到同样的问题**，这是未来该自动化的一环（从 clip 自动读长度）。

> **注意 `rollSpeed` / `rollDuration` / `hideDuration` 三项对 Werewolf 是无用的**，
> 但你没法删——删了 Shell 就坏了。
> **这就是"配置类被两只怪同时污染"的具体样子。**

### 为什么是这个顺序（这一段必须理解，不能照抄）

**优先级的三条原则**：

1. **紧急的在前**：死亡 > 受击。（受击要能被任何东西打断，除死亡）
2. **一次性的在前**：警戒、施法都在"持续性行为"之前。
   因为如果追击在前，警戒永远不会触发——追到一半已经满足 `HasTarget` 了。
3. **靠冷却互斥，不靠顺序**：重击和近战的距离条件完全一样（0~2.2），
   但重击有独立冷却（3 秒）。冷却到了它就抢走机会，冷却中是 `Failure`，让位给近战。
   **这就是冷却条件的作用：让两个范围重叠的分支能共存。**

**关于"目标在身后"为什么不需要一条分支**：

第一版有一条 `TargetBehind → TurnToTarget` 分支，用来先转身再攻击。

**第二版删掉了。** 因为转向已经交给 `CustomNavAgent`：

- 追击时：`Agent.SetDestination` 每帧刷新，Agent 按 `turnSpeed` 已经在转了
- 攻击时：`AttackState.OnEnter` 里的 `FaceTowards` 会瞬时摆正朝向

所以"背对着挥爪"这个风险已经被 `FaceTowards` 消掉了，不需要额外分支。

**删掉它的额外好处**：行为树从 12 条降到 11 条，少一条要维护的逻辑。

---
- 100 度以内说明"大致朝前"，可以直接攻击（判定框有宽度）
- 超过 100 度必须转身，否则打空

**关于分支 8/9/10 区间重叠**：
- 远程 6~11、扑击 2.5~7、跃击 7~11 都有重叠
- 重叠没关系，靠**顺序 + 冷却**决定谁先。远程（分支 8）在前，所以 6~11 米优先射；
  射不了（冷却中）才轮到扑击/跃击。

**关于分支 12 兜底为什么必须有**：
如果没有 `Always → Idle`，所有分支都 `Failure` 时
（比如没目标、没受击、没死），`_root.Evaluate` 返回 `Failure`，
`_currentState` 保持上一次的状态继续跑。
结果可能是**怪物保持"追击"状态对着空气走**。

## 8.2 归类：现有架构的复杂度来自哪三处

### 复杂度 1：数据分三处，加能力要同时改三处

```
能力（比如"重击"）
  ├─ 配置数值 → EnemyAIConfig + EnemyBrain 属性      ← 2 处
  ├─ 运行时状态 → EnemyBlackboard 字段               ← 1 处
  └─ 触发条件 → ConditionType + ConditionFactory     ← 2 处
```

再加状态类（1 个）+ 工厂注册（1 处）= **6 个地方**。

**为什么痛苦**：你只想加一个"重击"，却要在 6 个文件之间来回跳。
每次都要重新定位"我刚写到哪了"。

### 复杂度 2：枚举只能往后加，插入就静默错位

`EnemyStateType` 和 `ConditionType` 的整数值**存在资产里**。

```yaml
# WerewolfAI.asset 里的行为树
action: 4     # ← 这个 4 是写死的整数，对应 EnemyStateType.Dead
```

如果你在枚举中间插入一个值：

```csharp
Idle, Chase, NEW_STATE, AttackMelee, ...   // ← 插入一个
//                          ↑ 原本 AttackMelee=2，现在变成 3
```

所有旧资产里的 `action: 2` 会**突然指向 NEW_STATE**，而且**不报错**。

**这不是假设，是真实风险。** 这也是为什么阶段 4、5 都强调"只能往后加"。

### 复杂度 3：条件工厂是复制粘贴

```csharp
case ConditionType.CooldownAttackReady:  return b => Time.time - b.BB.LastAttackTime  >= def.p1;
case ConditionType.CooldownRollReady:    return b => Time.time - b.BB.LastRollTime    >= def.p1;
case ConditionType.CooldownHeavyReady:   return b => Time.time - b.BB.LastHeavyTime   >= def.p1;
case ConditionType.CooldownPounceReady:  return b => Time.time - b.BB.LastPounceTime  >= def.p1;
case ConditionType.CooldownLeapReady:    return b => Time.time - b.BB.LastLeapTime    >= def.p1;
case ConditionType.CooldownRangedReady:  return b => Time.time - b.BB.LastRangedTime  >= def.p1;
case ConditionType.CooldownSpellReady:   return b => Time.time - b.BB.LastSpellTime   >= def.p1;
```

**7 个 case，逻辑完全一样，只有字段名不同。**

而你在阶段 7 已经亲身体验过后果：**`LastRangedTime` 写成了 `LastSpellTime`，肉眼查不出来。**

## 8.3 共性：两只怪到底共享什么

### 共享的（可以抽象）

| 共性 | Shell | Werewolf | 说明 |
|---|---|---|---|
| 感知方式 | 球形扫描 + 迟滞 | 同 | 完全一样的逻辑 |
| 移动方式 | A* 寻路 | 同 | 完全一样 |
| 攻击流程 | 播动画 + 发事件 + 开窗口 | 同 | 完全一样 |
| 受击反应 | 停 + 播受击 + 等硬直 | 同 | 完全一样 |
| 死亡处理 | 停 + 播死亡 + 关感知 | 同 | 完全一样 |
| **移动类状态** | `Chase` | `Chase` | **代码复用，0 改动** |
| **待机类状态** | `Idle` | `Idle` | 复用 |
| **受击类状态** | `Hit` | `Hit` | 复用 |
| **死亡类状态** | `Dead` | `Dead` | 复用 |

**现有 8 个状态里复用了 6 个**（Idle / Chase / AttackMelee / AttackRanged / Hit / Dead）。
这说明：**"通用动作"确实存在，而且占了多数。**

### 不同的（不能抽象，或者说抽象了也没用）

| 差异 | Shell | Werewolf |
|---|---|---|
| 攻击种类 | 1 近战 + 1 远程 | 4 近战 + 1 远程 + 1 施法 |
| 特殊位移 | 滚动（无攻击） | 扑击、跃击（带攻击） |
| 防御能力 | 缩壳（减伤） | 无 |
| 警觉反应 | 无 | 张望 |
| 转向表现 | 无 | 有 Turn 动画 |
| 参数名 | `Speed`/`Attack`/`Roll`… | `MoveSpeed`/`Melee`/`Pounce`… |

### 一个重要的观察

看"不同的"这一列——**注意它们不是"能力不同"，而是"能力的有无"不同**：

```
Shell 有能力集合：{近战, 远程, 滚动, 缩壳}
Werewolf 能力集合：{近战x4, 远程, 扑击, 跃击, 施法, 警戒, 转向}
```

**交集**：近战、远程
**并集**：近战、远程、滚动、缩壳、扑击、跃击、施法、警戒、转向

如果现在做通用框架，你会按**并集**设计——给所有怪预留"扑击""跃击""施法""警戒"的位置。
但 Shell 永远用不上后四个，于是它身上背着 4 份死配置。

> **这就是"做 2 只怪不够"的核心原因**：
> 你手上的样本只有 2 个，你无法判断哪些是"真正通用的"，哪些是"这个游戏恰好有的"。
> 按并集设计 = 过度设计；按交集设计 = 不够用。

## 8.4 判断：为什么需要 3~4 只怪才能提炼

### 论证 1：2 个样本无法区分"共性"和"巧合"

假设你手上只有 Shell 和 Werewolf：

| 观察到的现象 | 可能是"通用规律" | 也可能是"巧合" |
|---|---|---|
| 两只怪都有"近战" | 所有怪都有近战 | Shell 和 Werewolf 恰好都是近战怪 |
| 两只怪都有"远程" | 所有怪都有远程 | 恰好都有 |
| 两只怪都没有"治疗" | 怪物不需要治疗 | 恰好都没做 |

**加入第 3 只怪（假设是"治疗型牧师怪"）**，立刻推翻第三条：
原来"治疗"是需要的，只是前两只恰好没有。

**每加一只怪，你都可能推翻前面的判断。**

### 论证 2：抽象的错误代价，随使用次数放大

假设你现在（2 只怪时）就抽象出一个"通用攻击系统"：

```csharp
public enum AttackKind { Melee, Ranged, Pounce, Leap, Heavy, Spell }
```

到第 3 只怪（比如一只只会吐毒的蛇），你会发现：

- 它没有近战 → `Melee` 是死枚举值
- 它的"吐毒"既像远程又像持续伤害 → 塞不进这个 enum

**你要改的这个 enum，已经被 3 只怪的配置引用了。**
改一次，3 份资产全要跟着改，而且改错了**不报错**（就是前面说的整数错位）。

> **抽象越早，返工代价越大。**
> 因为抽象会被数据引用，而数据不会报错。

### 论证 3：你需要看到"第三只怪推翻第一只怪假设"的完整过程

真正有价值的通用框架，不是"把 2 只怪合并"，而是**经历过假设被推翻还能站住**。

这在工程上有个名字：**Rule of Three（三次法则）**。

> 第一次做，你只是解决问题。
> 第二次做，你注意到重复，但还不确定该抽什么。
> 第三次做，你终于能看出**哪些重复是本质的，哪些是表象的**。
> 这时候抽象，成功率最高。

### 论证 4：你已经能预判第 3、4 只怪会推翻什么

用现在的两只怪，就能列出"下一个抽象假设可能错在哪"：

| 你现在可能想抽的 | 第 3 只怪可能怎么推翻它 |
|---|---|
| "所有怪都有 `Melee`" | 加一只只会远程的法师 → `Melee` 变成可选 |
| "所有怪都有 `Chase`" | 加一只固定炮台（不移动）→ `Chase` 也要可选 |
| "所有怪的受击都是停 + 硬直" | 加一只霸体怪（受击不停）→ 受击变成可配置 |
| "所有怪死亡都关感知" | 加一只死后爆炸的怪 → 死亡要加"死亡效果" |
| "参数名固定 13 个" | 加一只会召唤的怪 → 要加 `Summon` |

**这张表就是"为什么还要 3~4 只"的具体答案**：
每一个你现在想当然的假设，都可能在下一只怪身上被推翻。

## 8.5 那现在应该做什么

**不做通用框架，但做三件低成本的事**：

### 事 1：把命名契约固定下来（已做）

`参数命名契约 v1` 已经写进阶段 0。**这是唯一现在就该固化的东西**，因为：

- 它不依赖样本数量（名字对不对，跟有几只怪无关）
- 它一旦错，会污染所有后续代码
- 它的成本是 0（只是约定）

### 事 2：记录每只怪给你带来的"意外"

开一个文件，每加一只怪就记两行：

```markdown
## Werewolf（第 2 只）
- 意外：能力数量差异这么大（4 近战 vs 1 近战）
- 逼出的改动：接口加了 PlayAction(actionId)，因为不想加 7 个方法
```

**这些"意外"就是未来抽象的原料。** 记满 4 只，你会发现真正的共性清单自然浮现。

### 事 3：第 3 只怪开始，专门观察"重复到第 3 次"的东西

具体观察三个指标：

| 指标 | 判定标准 | 到了就该抽 |
|---|---|---|
| 同一个 `switch`/`if` 写第 3 次 | 比如 `PlayAction` 里的 case 分支 | 改成数据表 |
| 同一个字段在 3 个类里重复 | 比如 `LastXxxTime` | 改成 key 化容器 |
| 同一段 3 行样板写第 3 次 | 比如 `EnemyBrain` 的属性 | 改成统一注入 |

**用"3 次"而不是"2 次"作为标准，就是 Rule of Three 的实操形态。**

> **有某个能力时，必须用这个名字；没有时，就不建这个参数。**

| 没用（8 个） | 原因 |
|---|---|
| `Walk Forward W Root` | 带根位移，会和代码移动打架 |
| `Run Forward W Root` | 同上 |
| `Pounce Smash Attack W Root` | 同上 |
| `Jump W Root` | 同上 |

| `Jump In Place` | 原地跳，无位移无攻击，塞进状态机只会莫名弹跳 |
| `Turn Left` | **转向由 `CustomNavAgent.turnSpeed` 负责，不由动画表现** |
| `Turn Right` | 同上 |

**为什么排除了 8 个还要专门说一句**：

"必须用上全部动作"这句话如果理解成"22 个动画都得塞进状态机"，会做出错误的设计。

正确的理解是：**每个有战斗语义的动作要有归属**。

- 5 个 `W Root` 是**技术重复**（同一动作的带位移版），排除是因为会和代码抢移动权
- `Jump In Place` 是**无语义**（原地跳，不构成任何战斗行为）
- `Turn Left` / `Turn Right` 是**职责错配**（转向归寻路系统，不归动画系统）

**能说出"为什么不用"，比"全都用上"更能说明你理解了。**
