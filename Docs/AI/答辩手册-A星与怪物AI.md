## 2 A* 寻路（6 分钟）

### 2.1 先回答"为什么自己写"

**约束**：需要精确控制重规划频率、转向插值、路径可视化，且研究对象是架构本身。

**三个理由（按重要性排）**：

1. **可控性**：自研能精确决定"多久重算一次、算到第几个航点、转向用多快的插值"，NavMesh 这些是黑盒。
2. **可观测性**：我用 Gizmos 实时画出网格与路径，调试时能直接看到"它为什么绕这条路"，这是答辩演示的关键素材。
3. **研究目标**：直接调 API 就无法暴露模块间的耦合问题，也就无从设计。

**必须补一句诚实的话**（这句是加分项）：

> "但如果目标是快速产出商业产品，我会直接用 NavMesh。这里的选择是服务于研究目标，不是工程效率。"

### 2.2 四层职责（一句话一层）

| 层  | 类                | 职责                                                          | 关键设计                                          |
| -- | ---------------- | ----------------------------------------------------------- | --------------------------------------------- |
| 数据 | `Node`           | 一个格子：`walkable` / `gCost` / `hCost` / `parent`              | 节点是**全局共享**的，所以每次搜索后必须复位                      |
| 空间 | `GridManager`    | 把世界切成网格，用 `Physics.CheckSphere` 一次扫描标记不可行走                  | 单例，`gridSize = round(worldSize / (2×radius))` |
| 算法 | `AStarAlgorithm` | 纯静态、无状态，`FindPath` 进、`List<Node>` 出                         | 不持有任何字段，可被任意调用方复用                             |
| 执行 | `CustomNavAgent` | 对标 `NavMeshAgent`：`SetDestination` / `Stop` / `FaceTowards` | 0.2s 重规划、0.5m 航点容差、`Slerp` 转向                 |

**这四层分离的收益**：算法层完全不知道怪物存在，所以它能被单独测试、单独替换（换成 JPS 只改这一层）。

### 2.3 算法核心：一句话 + 一个公式

> A* 的本质是"**已付出的代价 + 预估还要付出的代价**"作为优先级，每次从开放列表里取最小的那个展开。

```
f(n) = g(n) + h(n)
g(n)：从起点到 n 的实际代价（已付出）
h(n)：从 n 到终点的估计代价（预估）
```

**关键实现细节（老师很可能追问）**：

| 细节    | 我的做法                                                 | 为什么              |
| ----- | ---------------------------------------------------- | ---------------- |
| 选最小节点 | `openSet` 是 `List<Node>`，**线性扫描**比较 `f`，`f` 相同则比 `h` | 实现简单；代价是 O(n)    |
| 松弛条件  | `新 g < 旧 g` 或 `不在 openSet` 才更新                       | 标准松弛             |
| 已关闭节点 | **直接 `continue`，永不重开**                               | 依赖 h 的一致性（下面讲）   |
| 回溯    | 从终点沿 `parent` 走回起点，再 `Reverse`                       | 得到正向路径           |
| 复位    | 搜索结束把 `gCost/hCost/parent` 清零                        | 节点共享，不复位会污染下一次搜索 |

### 2.4 为什么是 14 / 10（这是最容易被问的点）

```csharp
int dstX = |a.x - b.x|, dstY = |a.y - b.y|;
if (dstX > dstY) return 14 * dstY + 10 * (dstX - dstY);
return 14 * dstX + 10 * (dstY - dstX);
```

这是 **Octile 距离**：直走一步代价 10，斜走一步代价 14。

**为什么不用欧氏距离**：`√(dx²+dy²)` 每次要开方，浮点开销大，而且浮点比较容易出现 `f` 相等判断的精度问题。

**为什么不用曼哈顿距离**：曼哈顿假设只能走直角，对 8 方向移动会**高估**代价（斜走实际只花 14，它算 20），导致 h 不可采纳 → **不保证最优**。

**为什么 14 是安全的**：真实斜走代价是 `10√2 ≈ 14.142`，取 14 **略小于**真实值 → h 永远不会高估 → **可采纳（admissible）**。

**更强的一条性质**：14/10 还满足**一致性（consistent）**，因为 `14 ≤ 10√2`。一致性保证"沿路径的 f 值单调不减"，所以**第一次弹出某节点时它的 g 已经最优**——这就是代码里敢直接 `continue` 掉已关闭节点的原因。

> 这段话是全章的技术高点。如果老师只记住一件事，让他记住这个。

### 2.5 复杂度：主动交代瓶颈

| 操作                            | 当前实现        | 复杂度                  |
| ----------------------------- | ----------- | -------------------- |
| 取 f 最小节点                      | 线性扫描 `List` | O(n)                 |
| `openSet.Contains` / `Remove` | 线性查找        | O(n)                 |
| 整体                            | —           | **O(V²)**（V = 扩展节点数） |
| 理论最优                          | 二叉堆         | O(V log V)           |

**并且主动说第二层瓶颈**：

- `GetNeighbors` 每次 `new List<Node>()`，一次搜索要分配几百个小对象 → GC 压力 → 帧率抖动。
- **没有对角切角检查**：允许从两个阻挡格之间斜穿，贴墙时会"擦角"。

**优化路径（说清楚，不要含糊）**：

1. `openSet` 换二叉堆 / 索引堆 → 取最小 O(log n)；
2. `GetNeighbors` 复用预分配缓冲区（8 个固定槽位）；
3. 加切角检查：斜走前先判断两个正交邻居是否都可走；
4. 路径平滑：现在只有"航点提前切换 + `Slerp` 转向"，**没有视线简化**；要做真正的平滑需要 string pulling 或漏斗算法。

### 2.6 代理层：为什么 0.2 秒而不是每帧

| 参数                     | 值    | 作用                |
| ---------------------- | ---- | ----------------- |
| `pathUpdateInterval`   | 0.2s | 重规划间隔             |
| `nextWaypointDistance` | 0.5m | 提前切下一个航点，避免"到点急停" |
| `stoppingDistance`     | 1.5m | 进这个距离就停，不贴脸       |
| `turnSpeed`            | 10   | `Slerp` 转向速度      |
| 卡住检测                   | 0.5s | 位移过小则重新寻路         |

**讲述逻辑**：目标每帧都在动，但**路径不需要每帧都是最优**。0.2 秒的滞后人眼几乎察觉不到，而寻路开销从"每帧一次"降到"每秒 5 次"，这是典型的**用精度换吞吐**。

### 2.7 量化数据（如果老师问"有数据吗"）

算法级基准（同一套边权、同一套选优规则的等价实现，统计与语言无关的**扩展节点数**与**比较次数**）：

| 网格            | 扩展节点  | 比较次数      |
| ------------- | ----- | --------- |
| 20×20         | 15.1  | 276.6     |
| 100×100       | 152.9 | 15 112    |
| 100×100（二叉堆版） | —     | **159.5** |

**这张表能同时证明两件事**：① 线性扫描的比较次数随规模平方增长；② 换成堆之后降到同一量级，验证了 O(V²) → O(V log V)。

> 诚实边界：这是**算法级**统计，不是 Unity Profiler 的真机帧时间。如果老师追问"游戏里到底多少毫秒"，如实说"这一项我还没做真机 profile，是下一步工作"。

## 3 怪物 AI（8 分钟）

### 3.1 核心命题：我把行为树压平了

**这是整个 AI 部分唯一需要老师记住的事。**

> "常规做法是行为树。我没有用，因为在我的需求下，行为树的能力有 80% 用不上，而它的成本（节点资产、编辑器、运行时递归、策划学习曲线）是 100% 要付的。所以我把它压平成了一张表。"

**压平的等价关系**：

| 行为树概念           | 表里的对应物                                   |
| --------------- | ---------------------------------------- |
| `Selector`（选择器） | 整张规则表，自上而下第一条全真即返回                       |
| `Sequence`（顺序器） | 一条规则下的所有条件（AND）                          |
| `Condition` 叶子  | 条件表的一行                                   |
| `Action` 叶子     | 规则行的 `Action`（只有 ability / chase / idle） |
| 节点优先级           | `RuleIndex` 越小越优先                        |

**能压平的三个前提（缺一不可，这句很关键）**：

1. 决策深度只有两层：优先级 + 条件合取，**没有三层嵌套**；
2. 条件之间**只有 AND**，没有 OR、没有"非"、没有装饰器；
3. 动作是"**发起即结束**"，不是需要持续 tick 的节点（持续逻辑下沉到执行器）。

**收益**：策划能直接编 Excel；Git diff 能看出"谁把阈值从 0.3 改成 0.5"；求值无递归、无分配，成本恒定为 O(规则数 × 条件数)。

**代价（必须自己说出来）**：丢掉 OR 组合、嵌套子树复用、节点记忆（"上次打到第几段"）、`Running` 三态。

**边界（这句是加分项）**：

> "所以它有一个明确的抽象边界：一旦 Boss 需要'阶段记忆 + 或条件'，就该升级成真正的行为树，而不是继续给表加列。"

### 3.2 三层状态机（为什么不是一层）

| 层  | 名字                       | 状态                | 变化频率   | 回答什么问题        |
| -- | ------------------------ | ----------------- | ------ | ------------- |
| L1 | `EnemyBrain.RuntimeMode` | 待机 / 战斗 / 硬直 / 死亡 | 整场几十次  | **现在能不能接新决策** |
| L2 | 能力生命周期                   | 就绪 / 执行 / 中断 / 已用 | 每次出招一轮 | **正在做什么**     |
| L3 | Animator Controller      | 各动画状态             | 每次动作   | **看起来在做什么**   |

**关键点**：L1 里**没有"攻击"这个状态**。攻击不是模式，是能力。这正是旧版"每招一个状态类"被取消的地方——10 个招式 × 4 个阶段 = 40 个类，现在变成 1 个运行时 + 7 个执行器。

**L1 的四条迁移**（讲的时候配状态图）：

| 当前 | 触发        | 目标      | 副作用                           |
| -- | --------- | ------- | ----------------------------- |
| 任意 | 规则命中      | 战斗      | 解锁移动 + `SetDestination`       |
| 战斗 | 收到受击事件    | 硬直      | `Abort()` + 记录硬直结束时间 + 试播受击动画 |
| 硬直 | 能力结束且计时到期 | 战斗 / 待机 | 有目标回战斗，否则待机                   |
| 任意 | 血量归零      | 死亡      | 中断 + 锁移动 + 关感知（不可逆）           |

### 3.3 五张表的分工

| 表                          | 一行代表 | 回答什么                 |
| -------------------------- | ---- | -------------------- |
| `MonsterAI`                | 一只怪  | 视野、速度、硬直、动画参数名       |
| `MonsterAbility`           | 一个招式 | 怎么动、打多少、多久、多远        |
| `MonsterBehavior`          | 一条规则 | 什么情况下用哪招             |
| `MonsterBehaviorCondition` | 一个条件 | 这条规则要满足什么            |
| `MonsterAnimation`         | 一条映射 | 语义键 → Animator 真实参数名 |

**装配**：`TryGet(tid)` 命中缓存则直接返回，未命中则 `Build()` 做四次 join，把五张表拼成一个**只读定义对象**。运行期再也不碰原始表。

**为什么要拼成一个对象**：因为运行期如果每次都查表，字段散落在五个字典里，任何一处改键都会引发连锁。拼成对象之后，**"一只怪的完整行为"是一个不可变值**，可以整体缓存、整体校验。

### 3.4 决策链（一条链讲完）

```
EnemyBrain.Update()
├─ EnemyPerception.Tick(BB)      每 0.2s 扫一次，写 Target / DistanceToTarget
├─ RefreshHpRatio()              写 HpRatio
├─ 三个守卫：死亡 / 硬直 / 正在出招 → 提前 return
└─ EvaluateBehavior()
   ├─ BehaviourRuleSelector.Select(...)    第一条全真规则胜出
   │  └─ FindExecutableAbility(id, slot)   ID 优先，失败回退槽
   └─ StartAbility(ability)
      └─ 按 executor 建实例 → 记账冷却 → Executor.Start
```

**两个值得单独讲的设计**：

1. **黑板只有 5 个字段**（`Target` / `DistanceToTarget` / `CanSeeTarget` / `HpRatio` / `LastHitTime`）。感知和决策之间只有这一个契约，所以感知换实现（比如换成射线检测）决策层不用改。
2. **决策不是每帧都跑**。三个守卫让"出招期间不做决策"成为结构性保证，而不是靠程序员自觉写 if。

### 3.5 执行器与动画契约

**7 个执行器**：`attack` / `ranged_attack` / `dash` / `dash_attack` / `stance` / `play_and_wait` / `dead`。

**每个执行器只回答"这一次"的过程**：命中判定什么时候发、位移怎么施、姿态什么时候收。**跨次的状态（冷却、用过没有）归运行时**——这条边界一旦搞混，冷却就会随执行器重建而清零。

**动画契约**：AI 侧永远只说语义键（`action.melee`），不碰 Animator 参数名。

```
能力表：AnimationAction = "action.melee"
  → 动画表：action.melee / Trigger / "Melee"
    → Animator.SetTrigger(hash("Melee"))
```

**收益**：换模型只改表的第四列，代码零改动。**代价**：多一层间接，读表要跳两跳。

**三道关卡**：导出时校验枚举合法 → 启动时校验绑定存在 → 运行时校验参数类型匹配。**任何一道不过，怪物不生成**——不会带着半套绑定跑起来。

### 3.6 为什么这么设计（三个约束）

| 约束             | 应对                   |
| -------------- | -------------------- |
| 怪物种类会增加，但代码不想改 | 五张表 + 启动校验，加怪零代码     |
| 策划要能自己调数值      | Excel 工作台 + 20 条校验规则 |
| 一帧只有 16 毫秒     | 决策无递归无分配；寻路 0.2s 一次  |

## 5 高频问题与答法（20 题）

### A 组：项目定位

**Q1：这不就是个 Unity 小游戏吗？拖拖拽拽就能做吧？**

> "引擎提供渲染、物理、动画这些基础设施，但**引擎不提供架构**。它给你 `Rigidbody` 和 `Animator`，但不会告诉你决策逻辑和动画播放该怎么解耦、攻击判定该按什么维度分层。这 7 千行全部是这部分架构代码。类比一下：数据库提供存储能力，但表结构设计仍然要人来做。"

**Q2：代码量不多，工作量够吗？**

> "7 千行运行时代码 + 2 700 行编辑器工具 + 36 份文档。而且**代码量是刻意控制的结果**：统一战斗实体接口之后，怪物和玩家共用一条攻击管线，如果不用接口，怪物就得复制一整套，代码量翻倍但质量下降。所以代码少是架构的结果，不是工作量不足。"

**Q3：创新点是什么？**

> "我不太用'创新'这个词，容易和'首创'混淆。更准确的说法是三点工程贡献：一是把行为树压平成规则表，并给出了压平成立的三个前提；二是用'能力对象 + 执行器策略'替代'每招一个状态类'；三是建立了一套启动期校验，把配置错误挡在运行之前。"

**Q4：为什么只有两只怪？**

> "因为我验证的是**机制**不是**规模**。加第三只怪只需要填五张表，代码零改动——这一点我可以现场演示。但我也承认，两只怪不能证明规模上的可扩展性，真正的验证需要 10 只以上的怪和更复杂的规则。"

### B 组：A*

**Q5：为什么不用 NavMesh？**

> "三个原因：可控性（重规划频率、转向插值我能精确控制）、可观测性（Gizmos 能画出路径，答辩演示需要）、研究目标（直接调 API 就无法暴露耦合问题）。但如果是做商业产品，我会直接用 NavMesh——这里的选择服务于研究目标，不是工程效率。"

**Q6：你的 A* 保证最优吗？**

> "保证，前提是启发函数可采纳。我用 Octile 距离，直走 10、斜走 14，而真实斜走是 14.142，所以 h 永远不高估真实代价，满足可采纳性。"

**Q7：为什么可以直接跳过已关闭节点，不重开？**

> "因为 14/10 不仅可采纳，还满足**一致性**：`14 ≤ 10√2`。一致性保证沿路径 f 单调不减，所以第一次弹出某节点时 g 已经最优，不需要重开。如果换成会高估的启发函数（比如曼哈顿），这个优化就是错的。"

**Q8：复杂度多少？**

> "当前是 O(V²)，因为开放列表是 `List`，取最小要线性扫描。理论上用二叉堆可以到 O(V log V)。我做过等价实现的基准：100×100 网格下比较次数从 15 112 降到 159.5。"

**Q9：8 方向移动会不会穿墙角？**

> "会。当前没有做切角检查，斜走时只判断目标格可走，不判断两个正交邻居，所以贴墙时会擦着墙角过去。修法是斜走前先检查两个正交邻居，这是已知待修项。"

**Q10：路径不平滑怎么办？**

> "目前只有两层处理：航点提前 0.5 米切换，避免到点急停；朝向用 `Slerp` 插值。**没有做视线简化**。真正的平滑要用 string pulling 或者漏斗算法，把能直连的航点合并掉。"

**Q11：动态障碍怎么办？**

> "靠 0.2 秒的定时重规划，加上 0.5 秒的卡住检测。但这是"整条重算"，不是增量修复。更合适的做法是 D* Lite 这类增量算法，只修复受影响的那一段。"

**Q12：为什么每次搜索后要复位节点？**

> "因为网格是单例、节点是全局共享的。不复位的话，上一次搜索留下的 `gCost` 和 `parent` 会污染下一次，导致路径走错。这也意味着我的寻路实现**不可重入、非线程安全**。"

### C 组：怪物 AI

**Q13：为什么不用行为树？**

> "因为在我的需求下，行为树 80% 的能力用不上，成本却是 100% 要付的。压平成立有三个前提：决策只有两层、条件只有 AND、动作发起即结束。这三个前提我都满足，所以我用一张表替代了它。代价我也清楚：丢掉 OR、嵌套、节点记忆。"

**Q14：规则表能表达"或"吗？**

> "不能直接表达。但可以用优先级模拟：把"或"拆成两条规则，条件分别是两个分支。比如"残血或脱战就逃跑"，就写成两条规则，前一条条件带血量阈值，后一条条件带距离。真正的嵌套或就需要升级数据结构了。"

**Q15：为什么能力是对象 + 执行器，而不是状态？**


> "状态类的数量是招式数 × 阶段数。10 个招式 4 个阶段就是 40 个类，而且每个类里都在重复'播动画、锁移动、等时间'。改成'能力对象描述数据 + 执行器描述过程'之后，7 个执行器覆盖了所有招式，加招式只填表。"

**Q16：动画为什么要走语义键，不直接播？**

> "因为 AI 不该知道 Animator 里参数叫什么。走语义键之后，换模型只改动画表的第四列，代码零改动。而且能在启动期校验：能力表里写的每个语义键，动画表里必须有对应行，否则怪物直接不生成。"

**Q17：数据驱动会不会改个表就崩？**

> "有 20 条启动校验挡着，覆盖引用完整性、数值合法性、必填项。但我要说清楚它的边界：**校验能保证"引用的东西都存在"，保证不了"语义是对的"**。比如一条攻击规则漏写了距离条件，语法上完全合法（空条件等于恒真），校验器抓不到，表现是怪物隔空挥爪。"

**Q18：加霸体要改多少？加多阶段 Boss 呢？**

> "霸体是小改：`AbilityDefinition` 加一个 `interruptible` 字段，`EnterStagger` 里判断一下，两处。多阶段 Boss 是结构性的：它需要阶段记忆和或条件，规则表撑不住，得升级成真正的行为树，或者至少加一层'阶段'维度。"

**Q19：决策每帧都跑吗？**

> "不是。`Update` 里有三个守卫：死亡、硬直、正在出招，三种情况都提前 return。所以决策频率等于空闲帧的帧率。这也意味着玩家感觉到的'反应慢'，往往是出招后摇太长，而不是决策慢。"

**Q20：这套东西最大的技术债是什么？**

> "三个。第一，招式 ID、槽名、执行器名全是裸字符串，拼错只能等启动或运行才发现，没有编译期检查。第二，数据有两个真相源：编辑器工作台写 txt，导出工具从 xlsx 覆盖 txt，谁后跑谁赢。第三，`EnemyBrain` 有 650 行，装配、状态机、事件、调试快照混在一起，改一处要读全文件。"

## 8 一页速查（打印带走）

**A\* 三个数字**：14 / 10（Octile）、0.2s（重规划）、O(V²)（当前复杂度）

**A\* 三句话**：
1. `f = g + h`，h 用 Octile，因为 14 ≤ 10√2 → 可采纳且一致；
2. 一致 → 可以不重开已关闭节点；
3. 瓶颈在开放列表的线性扫描，换堆能到 O(V log V)。

**AI 三句话**：
1. 行为树压平成规则表，前提是两层 + 全 AND + 发起即结束；
2. 三层状态机：模式（准入）/ 能力（过程）/ 动画（表现）；
3. 能力 = 数据对象 + 执行器策略，跨次状态归运行时。

**三个短板**：O(V²)、规则表无 OR、没有自动化测试。

**一句定位**：做的是运行时架构，不是小游戏。
