核心思想
决策与表现分离
AI 决定「做什么」，Animator 决定「长什么样」，两者通过参数通信，互不依赖。
技术选型
分层状态机（HFSM）
8 个行为用状态机足够；行为树留到 3 只怪以上再引入。
工作量
新写 6 个类
复用已有寻路 / 属性 / 伤害 / 事件 / 数据表，不重复造轮子。
终极目标
换怪只换动画
决策代码零改动 —— 做到它才算真正理解状态机。

一、三层分离架构（本系统的地基）

🧠 决策层 · EnemyBrain + IEnemyState + Blackboard
职责：读感知结果 → 决定当前状态 → 下发语义指令（ChaseTo / PlayAttack / StopMove）
严格不做：不碰 Animator 参数、不碰 Transform、不碰 Rigidbody
▼ 语义指令
🦵 执行层 · CustomNavAgent（已有） + EnemyCombat（新）
职责：真实位移（SetDestination）／真实伤害判定（发攻击事件）
严格不做：不碰 Animator、不做状态决策
▼ 状态广播（VelocityMagnitude / 攻击事件）
🎬 表现层 · EnemyAnimator（新） → Shell.controller
职责：把语义指令翻译成 Animator 参数（SetMoveSpeed / PlayBiteAttack）
严格不做：不读游戏状态（HP / 距离 / 目标）
为什么必须三层？你现在的 EnemyAI.cs 把「感知 + 决策 + 移动」全塞在一个 Update 里。行为增到 8 个时，这个类会膨胀到 500 行、无法维护。拆开后每个类都保持你项目一贯的单一职责水准。

三、Animator 重建方案（30 个平铺状态 → 4 个分区）

Base Layer │ ├── [Locomotion] ← 子状态机（默认入口） │ ├── Idle 循环 · Speed ≈ 0 │ └── Move 1D Blend Tree：Walk → Run │ ├── [Action] ← 子状态机 │ ├── BiteAttack 单次 · 近战 │ ├── ProjectileAttack 单次 · 远程 │ ├── CastSpell 单次 · 施法 │ └── Roll 单次 · 滚动 │ ├── [Reaction] ← 子状态机 │ ├── TakeDamage 单次 · 受击 │ ├── Hide 循环 · IsHidden = true │ └── Unhide 单次 · Hide to Idle │ └── Dead 单次 · 终止态，无出口
现状诊断：当前 Shell.controller 的 m_AnimatorParameters: [] —— 零参数，且状态名混乱（Idle 5 / Idle 6 / Idle 7、Walk Forward In Place 0/1），全靠 Exit Time 自动串联。这是「演示机」，AI 无法驱动。必须重建（保留文件本身，在内部清理）。

参数表（10 个）

参数类型用途
SpeedFloat0 = Idle，0.5 = Walk，1 = Run（驱动 Blend Tree）
IsDeadBool死亡锁，最高优先级
IsHiddenBool缩壳循环状态
AttackTrigger近战 Bite
ProjectileAttackTrigger远程
CastSpellTrigger施法
RollTrigger滚动冲刺
TakeDamageTrigger受击（Any State 打断）
DieTrigger死亡
UnhideTrigger出壳
关键原则：「程度渐变」用 Blend Tree（Idle↔Walk↔Run），「事件切换」用 State + Trigger（攻击 / 受击 / 死亡）。 绝不能用一个大 Blend Tree 混合攻击和死亡 —— 那是离散事件，不是插值关系。
Any State 三要点：① Can Transition To Self = false（否则受击动画自我打断、抽搐）；② 过渡到一次性状态时 Has Exit Time = false（否则失去打断意义）；③ Dead 无出口，IsDead 一旦为 true 永不复位。

四、组件挂载清单（新写 6 个 · 复用 3 个）

Shell (GameObject) [Layer: Monster] ← 必须是 Monster 层 ├─ Rigidbody 物理载体 · 必须加（CustomNavAgent 会读取） ├─ CapsuleCollider 受击体 ├─ Animator → 重建后的 Shell.controller ├─ CombatAttribute 复用 · HP/AD/DEF ├─ EnemyEntity 新写 · 数据桥接（替代 CharacterEntity） ├─ CustomNavAgent 复用 · 腿（寻路） ├─ EnemyPerception 新写 · 眼（视野扫描写黑板） ├─ EnemyAnimator 新写 · 嘴（语义级动画 API） ├─ EnemyCombat 新写 · 手（发起攻击判定） ├─ EnemyStateController 新写 · 锁（CanMove / CanAttack） └─ EnemyBrain 新写 · 脑（决策）★ 主入口
现状：你的 Shell.prefab 目前只有 1 个 Animator 组件，没有 Rigidbody、没有 Collider —— 而 CustomNavAgent.Awake() 会 GetComponent<Rigidbody>() 并设置旋转约束。不加 Rigidbody 会直接报空引用。

五、必须先修的 4 个架构缺口

缺口问题优先级
CombatDetector
只打 Monster 层		 _targetLayerMask = LayerMask.GetMask("Monster") —— 这是给玩家打怪物用的。怪物攻击玩家时依然只找 Monster 层 → 打不到玩家。需引入阵营概念：攻击者是 Player 则打 Monster，是 Monster 则打 Player。 🔴 阻塞
EnemySpawner
计数只增不减		 _currentEnemyCount++ 但怪物死亡无人减 → 刷满 maxEnemies 后永久停止刷怪。需监听 EnemyDieEvent 回调减计数。 🟡 需修
CharacterEntity
依赖存档数据		 它 Initialize() 读 saveData.CurrentHP，怪物没有 CharacterData → 空引用。建议新写 EnemyEntity（只读 CharacterDefine）。 🟡 需修
CharacterDefine.txt
没有 Shell 条目		 目前只有 MC17 / MC19 / CapsuleEnemy。需新增 Shell（TID 2001），且 SubType 必须与 AttackDefine 的 ComboGroup 完全一致。 🟡 需修

六、开发阶段（每个阶段端到端闭环）

阶段一
活过来
挂组件 + 重建 controller（Locomotion）+ Perception + Brain（Idle/Chase）
验证：螃蟹能发现玩家并追过来
阶段二
能打人
修 CombatDetector 阵营 + EnemyCombat + Action 分区 + AttackMelee
验证：靠近后咬人，玩家掉血
阶段三
受击与死亡
StateController + Reaction 分区 + Dead + Any State 打断
验证：打螃蟹会打断动作，打死播死亡
阶段四
变聪明
远程 + 冷却 + 缩壳减伤 + 滚动冲刺
验证：远距离放远程、残血缩壳、中距滚过来
本阶段严格不做：行为树、Root Motion、群体 AI / 仇恨转移、寻路算法修改、玩家侧逻辑修改、动画资源重命名。

七、最终目标

  • 换一只怪物（如 Snake），只需换动画和参数，决策代码零改动。
  • 做到这一条，说明你的 AI 与具体怪物真正解耦了 —— 这才是"商业开发流程"和"能跑就行"的分水岭。
  • 届时再把 EnemyBrain 的决策内核替换为行为树，现有状态类可整体复用为行为节点，不会白写。
