# 4. ARPG 怪物 AI 与状态机系统策划方案

> 承接 `0.底层框架搭建` / `1.ARPG 输入与角色行为系统结构策划方案` / `2.ARPG 角色受击系统` / `3.ARPG 角色跳跃·二段跳·空中翻系统`。
> 本方案以 **Shell(小螃蟹)** 作为第一个怪物样本，目标是把一个"会走路的模型"变成一个"有决策能力的敌人"。
> 开发原则与第 1 号策划案完全一致：**职责分离、单模块闭环验证、先跑通再加行为**。

## 一、系统概述

### 1.1 一句话架构

> **小螃蟹的"聪明"不在 Animator 里，而在 AI 决策层。**
> Animator 只回答"我现在长什么样"，AI 只回答"我现在该做什么"，两者通过参数通信，互不依赖。

这是理解整个系统的钥匙。你现在最大的困惑——"这么多行为这么多动作怎么控制"——本质上是因为把两件事混在一起想了。我们把它们拆开：

```text
决策层（EnemyBrain）        →  决定"做什么"（追击？攻击？缩壳？）
        ↓ 通过参数/指令
表现层（Animator）          →  决定"长什么样"（播哪个动画）
        ↓ 通过组件指令
执行层（CustomNavAgent）    →  决定"实际怎么动"（走到哪、转多少度）
```

三层之间**只允许向下发指令，不允许向上反查**。这与你第 1 号策划案里
`CharacterMovementController` 负责真实移动、`Animator` 负责表现的划分是同一个思想。

### 1.2 本系统负责

```text
├─ 怪物感知（看到玩家 / 距离 / 丢失目标）
├─ 怪物决策（状态机：待机 / 追击 / 攻击 / 缩壳 / 受击 / 死亡）
├─ 怪物移动指令（调用已有 CustomNavAgent）
├─ 怪物攻击执行（发起判定 → 复用已有伤害系统）
├─ 怪物动画表现（重建 Shell.controller）
└─ 怪物与数据表的绑定（复用已有 DataManager / CharacterDefine）
```

### 1.3 本系统不负责

```text
├─ 寻路算法本身（已有 AStarAlgorithm / CustomNavAgent，不改）
├─ 刷怪逻辑本身（已有 EnemySpawner，本阶段只做必要修正）
├─ 伤害计算公式（已有 DamageCalculator，不改）
├─ 玩家侧任何逻辑（不改 Character* 系列）
└─ 行为树（Behavior Tree）—— 见第三章决策，本阶段不引入
```

## 三、核心架构决策

这一章回答你最核心的问题：**FSM 还是行为树？为什么？**

### 3.1 概念澄清：FSM 与行为树不是一回事

很多人把两者混为一谈，但它们解决的是不同问题：

| | 有限状态机（FSM） | 行为树（Behavior Tree, BT） |
|---|---|---|
| 核心问题 | "我现在**处于什么状态**" | "我现在**该执行哪个行为**" |
| 运行方式 | 记住当前状态，只在条件满足时切换 | **每帧从根节点重新求值**，按优先级选一条路 |
| 强项 | 状态互斥、有明确阶段感（如：待机→追击→攻击） | 行为多、优先级会动态变化、需要组合与中断 |
| 弱项 | 状态一多，转移连线爆炸（N² 问题） | 对简单 AI 是**过度设计**，调试成本高 |
| 典型适用 | 敌人数量少、行为 < 10 个 | 行为 > 10 个、需要"打断/并行/优先级重排" |

**关键区别**：FSM 是"有记忆"的，BT 是"无记忆、每帧重新决策"的。

### 3.2 本阶段决策：采用分层状态机（HFSM），不引入行为树

**理由（商业开发视角）：**

1. **小螃蟹的行为只有 8 个**（待机/警戒/追击/滚动/近战/远程/缩壳/死亡），远未到 FSM 的连线爆炸临界点。
2. **行为树的价值在"组合与复用"**——你有 5 个、10 个怪物时才体现。第一个怪物上 BT，你会把 80% 时间花在写节点框架上，而不是怪物本身。
3. **你的项目已有 FSM 基因**：`EnemyAI.cs` 就是一个 Idle/Chase 状态机。演进比推倒重来成本低。
4. **符合第 1 号策划案原则**："先完成一个最小、完整、能够亲手验证的闭环"。

> **决策：第一个怪物（Shell）用分层状态机。**
> **行为树留到你有 3 个以上怪物、且行为开始重复时再引入**——那时你会非常清楚哪些节点需要复用，而不是凭空设计一套框架。

### 3.3 但我们用"行为树的思想"组织状态

虽然不写 BT 框架，但**决策顺序**借鉴 BT 的优先级思想，让状态判断天然有序：

```text
每帧决策优先级（从上到下，命中即停）：
  1. 我死了吗？            → Dead
  2. 我正在受击硬直吗？    → Hit（打断一切）
  3. 我的血量低于 30%？    → Hide（缩壳）
  4. 目标在近战距离内？    → AttackMelee
  5. 目标在中距离且冷却好？→ AttackRanged
  6. 我能看到目标？        → Chase
  7. 都没命中              → Idle
```

这段逻辑既可以用 `switch` 写（简单），也可以用状态类写（可扩展）。**本方案采用状态类**，因为你说要按商业流程做。

### 3.4 三层分离架构（本系统的核心图）

```text
┌─────────────────────────────────────────────────────┐
│  决策层  EnemyBrain + IEnemyState                    │
│  职责：感知结果 → 决定当前状态 → 下发指令            │
│  不碰：Animator / Transform / Rigidbody              │
└───────────────────┬─────────────────────────────────┘
                    │ ① 语义指令（ChaseTo / PlayAttack / StopMove）
┌───────────────────▼─────────────────────────────────┐
│  执行层  CustomNavAgent（已有） + EnemyCombat（新）   │
│  职责：真实位移 / 真实伤害判定                        │
│  不碰：Animator / 状态决策                            │
└───────────────────┬─────────────────────────────────┘
                    │ ② 状态广播（VelocityMagnitude / 攻击事件）
┌───────────────────▼─────────────────────────────────┐
│  表现层  EnemyAnimator（新） → Shell.controller       │
│  职责：把语义指令翻译成 Animator 参数                 │
│  不碰：游戏状态（HP / 距离 / 目标）                   │
└─────────────────────────────────────────────────────┘
```

**为什么必须是三层？**
因为你现在的 `EnemyAI.cs` 把"感知 + 决策 + 移动"全塞在一个 `Update` 里。当行为增加到 8 个时，这个类会膨胀到 500 行、无法维护、无法单测。
拆成三层后，每个类都保持在你项目一贯的"单一职责"水准上。


> **能追、能远能近、会挑攻击方式、残血会缩壳、被打会打断。**
> 这 5 条，就是这个状态机的全部目标。

## 五、AI 决策层设计

### 5.1 状态清单（8 个）

| # | 状态 | 进入条件 | 行为 | 退出条件 |
|---|---|---|---|---|
| 1 | `Idle` | 默认 / 丢失目标 | 播放 Idle，停止移动 | 看到玩家 → Alert |
| 2 | `Alert` | 首次发现玩家 | 原地转向玩家，短暂停顿（0.4s，给玩家反应时间） | 停顿结束 → Chase |
| 3 | `Chase` | 看到玩家且在追击距离 | `SetDestination(player)`，Speed 驱动 Walk/Run | 进近战距 → AttackMelee；中距+冷却好 → AttackRanged；丢失目标 → Idle |
| 4 | `RollChase` | 距离 3–7m 且 Roll 冷却就绪 | 播放 Roll，期间高速直线接近 | Roll 结束 → Chase |
| 5 | `AttackMelee` | 距离 ≤ 近战距离（约 1.6m） | 播放 Bite Attack，触发攻击判定 | 动画结束 → Chase（或再攻） |
| 6 | `AttackRanged` | 距离在远程区间（约 4–8m）且冷却就绪 | 播放 Projectile Attack / Cast Spell | 动画结束 → Chase |
| 7 | `Hide` | HP 比例 < 30% 且未缩壳 | 播放 Hide，停止移动，进入减伤 | 回复至 50% 或超时 → Chase |
| 8 | `Hit` / `Dead` | 受击事件 / 死亡事件 | 播放 Take Damage / Die | Hit → 返回上一状态；Dead → 终止 |

### 5.3 黑板（Blackboard）—— 状态的"共享内存"

状态之间不能互相持有引用，所有共享数据放黑板：

```csharp
public class EnemyBlackboard
{
    public Transform Target;          // 当前目标
    public float     DistanceToTarget;// 到目标距离
    public bool      CanSeeTarget;    // 感知结果
    public float     HpRatio;         // 当前血量比例
    public float     LastAttackTime;  // 上次攻击时间（算冷却）
    public float     LastRollTime;    // 上次滚动时间
    public bool      IsHidden;        // 是否处于缩壳
    public EnemyStateType PreviousState; // 用于 Hit 结束后回归
}
```

> **为什么需要黑板？**
> 因为"距离""冷却""血量"这些数据，多个状态都要用。如果每个状态自己去算，就会出现 8 份重复代码，且数据不同步。黑板让**感知层写一次、所有状态读**。

### 5.4 状态机实现范式（给第一次写状态机的你）

采用 **接口 + 状态类**，而不是巨型 `switch`：

```csharp
public enum EnemyStateType { Idle, Alert, Chase, RollChase, AttackMelee, AttackRanged, Hide, Hit, Dead }

public interface IEnemyState
{
    void OnEnter(EnemyBrain brain);
    void OnUpdate(EnemyBrain brain);   // 每帧
    void OnExit(EnemyBrain brain);
}
```

`EnemyBrain` 负责：持有所有状态实例、每帧调用 `current.OnUpdate`、提供 `ChangeState()` 入口。

```csharp
public class EnemyBrain : MonoBehaviour
{
    private readonly Dictionary<EnemyStateType, IEnemyState> _states = new();
    private IEnemyState _current;
    public EnemyBlackboard BB { get; } = new();

    public void ChangeState(EnemyStateType type)   // 唯一的状态切换入口
    {
        _current?.OnExit(this);
        _current = _states[type];
        BB.PreviousState = type;
        _current.OnEnter(this);
    }

    private void Update()
    {
        _current?.OnUpdate(this);
    }
}
```

**好处**：新增一个状态 = 新增一个类 + 注册一行，不碰其他状态。这就是"商业开发"和"能跑就行"的区别。

### 5.5 每个状态长什么样（以 Chase 为例）

```csharp
public class ChaseState : IEnemyState
{
    public void OnEnter(EnemyBrain b)
    {
        b.Agent.SetDestination(b.BB.Target.position);
    }

    public void OnUpdate(EnemyBrain b)
    {
        var bb = b.BB;
        bb.DistanceToTarget = Vector3.Distance(b.transform.position, bb.Target.position);

        // 决策优先级（见 3.3）
        if (bb.DistanceToTarget <= b.MeleeRange)      { b.ChangeState(EnemyStateType.AttackMelee); return; }
        if (bb.DistanceToTarget <= b.RangedRange &&
            Time.time - bb.LastAttackTime > b.AttackCooldown) { b.ChangeState(EnemyStateType.AttackRanged); return; }
        if (!bb.CanSeeTarget)                          { b.ChangeState(EnemyStateType.Idle); return; }

        // 持续下达最新坐标
        b.Agent.SetDestination(bb.Target.position);
        b.Animator.SetMoveSpeed(b.Agent.VelocityMagnitude / b.RunSpeed);
    }

    public void OnExit(EnemyBrain b)
    {
        b.Animator.SetMoveSpeed(0f);
    }
}
```

> 注意：状态类里**只调用语义方法**（`SetMoveSpeed` / `SetDestination`），从不直接写 `_animator.SetFloat("Speed", ...)`。这与 `CharacterAnimator` 的封装思想完全一致。

## 六、动画表现层设计（重建 Shell.controller）

这是你问的第二个核心问题："这么多动作怎么组织？"

### 6.1 现状诊断

`Shell.controller` 目前的问题：

```text
✘ m_AnimatorParameters: []     → 零参数，AI 无法驱动
✘ 状态名混乱：Idle / Idle 5 / Idle 6 / Idle 7
              Walk Forward In Place 0 / Walk Forward In Place 1
✘ 全靠 Exit Time 自动串联     → 这是"演示机"，不是"可控制的状态机"
✘ 单层平铺 30+ 状态            → 无法组织
```

**结论：不能直接用，必须重建。** 但遵循你第 1 号策划案的约定——**保留 `Shell.controller` 文件本身，在其内部清理重建**（不新建 `ShellEnemy.controller`）。

### 6.2 重建后的结构：Sub-State Machine 分区

关键在于用 **Sub-State Machine（子状态机）** 把 30 个平铺状态收成 4 个语义分区：

```text
Base Layer
│
├── [Locomotion]  ← 子状态机（默认入口）
│   ├── Idle                          （循环，Speed ≈ 0）
│   └── Move                          （1D Blend Tree：Walk → Run）
│
├── [Action]      ← 子状态机
│   ├── BiteAttack                    （单次）
│   ├── ProjectileAttack              （单次）
│   ├── CastSpell                     （单次）
│   └── Roll                          （单次）
│
├── [Reaction]    ← 子状态机
│   ├── TakeDamage                    （单次）
│   ├── Hide                          （循环，IsHidden = true）
│   └── Unhide                        （单次，Hide to Idle）
│
└── Dead          （单次，终止态，无出口）
```

> 从 30 个状态 → **4 个分区 + 11 个状态**。这就是"组织"的意义。

### 6.3 Animator 参数表（最终版）

| 参数名 | 类型 | 谁写入 | 用途 |
|---|---|---|---|
| `Speed` | Float | `EnemyAnimator.SetMoveSpeed()` | 0=Idle，0.5=Walk，1=Run |
| `IsDead` | Bool | `EnemyAnimator.SetDead()` | 死亡锁 |
| `IsHidden` | Bool | `EnemyAnimator.SetHidden()` | 缩壳循环 |
| `Attack` | Trigger | `EnemyAnimator.PlayBiteAttack()` | 近战 |
| `ProjectileAttack` | Trigger | `EnemyAnimator.PlayProjectileAttack()` | 远程 |
| `CastSpell` | Trigger | `EnemyAnimator.PlayCastSpell()` | 施法 |
| `Roll` | Trigger | `EnemyAnimator.PlayRoll()` | 滚动 |
| `TakeDamage` | Trigger | `EnemyAnimator.PlayTakeDamage()` | 受击 |

> 参数命名与你的玩家侧保持同一风格（`Speed` / Trigger 语义化）。
> 玩家侧叫 `GetHit`，怪物侧叫 `TakeDamage`——因为怪物动画文件本身就叫 `Take Damage`，**以资源命名为准**（遵循第 1 号策划案约定）。
>
> ⚠️ **共 8 个参数**。原版列过的 `Die` / `Unhide` 两个 Trigger **已删除**，理由见 `5.2.缩壳状态机Hide-Unhide参数方案分析.md`：
> **持续状态用 `Bool`（`IsDead` / `IsHidden`），瞬时事件才用 `Trigger`。** 死亡与出壳都是持续状态，用 `IsDead == true` / `IsHidden == false` 表达即可，多一个 Trigger 只会制造"两个参数必须永远同步"的脆弱点。

### 6.4 核心过渡规则

**原则：用 Bool/Float 表达"持续状态"，用 Trigger 表达"一次性动作"。**

| 起点 | 终点 | 条件 | 说明 |
|---|---|---|---|
| Locomotion | Action | `Attack` / `ProjectileAttack` / `CastSpell` / `Roll` | 一次性动作，播完回来 |
| Action | Locomotion | `Has Exit Time = true`，`Exit Time ≈ 0.9` | 动作播完自动回归 |
| Locomotion | Hide | `IsHidden == true` | 缩壳是持续状态，用 Bool |
| Hide | Unhide | `IsHidden == false` | 出壳同样是持续状态的反面，仍用同一个 Bool |
| Unhide | Locomotion | `Has Exit Time = true` | 出壳动画播完回归 |
| **Any State** | TakeDamage | `TakeDamage` Trigger | **打断一切**（受击优先） |
| **Any State** | Dead | `IsDead == true` | 最高优先级，不可打断 |

**Any State 的使用要点（新手最容易踩的坑）：**
1. Any State → TakeDamage / Dead 是标准做法，用来实现"打断"。
2. **务必设置 `Can Transition To Self = false`**，否则受击动画会自己打断自己，产生抽搐。
3. Dead 状态**不设出口**，且要保证 `IsDead` 一旦为 true 永不复位（除非复活系统介入）。
4. Any State 过渡到一次性状态时，`Has Exit Time` 必须为 **false**，否则会等待当前动画播完才切，失去"打断"意义。

### 6.5 为什么不把所有动作都塞进一个 Blend Tree

常见错误：有人试图用一个巨大的 Blend Tree 混合 Idle/Walk/Run/Attack/Die。
**不行**，因为：
- Blend Tree 做的是**空间连续插值**（如走↔跑），适合同质动画。
- 攻击和死亡是**离散事件**，不是插值关系，必须用 State + Trigger。

> 记住这条分界线：**"程度渐变"用 Blend Tree，"事件切换"用 State。**

### 8.2 事件使用原则（延续第 1 号策划案）

> **EventBus 只广播"有意义的状态变化"，不广播连续数据。**

你项目里**已经有 `EnemyDamagedEvent` / `EnemyDieEvent`**，直接复用，不要新造。

## 九、必须解决的架构缺口（重要）

在做小螃蟹之前，有 4 个已有系统的问题会直接卡住你。**建议先修，再上 AI。**

### 9.1 🔴 `CombatDetector` 只打 Monster 层 —— 怪物打不动玩家

```csharp
// Combat/CombatDetector.cs 第 21 行
_targetLayerMask = LayerMask.GetMask("Monster");
```

**问题**：这个检测器是给**玩家攻击怪物**用的（打 Monster 层）。怪物攻击玩家时，它依然只会找 Monster 层 → **打不到玩家**。

**建议方案**：引入"阵营"概念，让检测器根据攻击者阵营选择目标层。

```text
攻击者是 Player  → 目标层 = Monster
攻击者是 Monster → 目标层 = Player
```

实现上最小改动是：在 `CharacterAttackHitEvent` 里携带目标层信息，或在 `CombatDetector` 里根据攻击者身上的标记判断阵营。**这一条不解决，第六阶段的攻击闭环无法验证。**

### 9.2 🟡 `EnemySpawner` 计数只增不减

```csharp
// AI/EnemySpawner.cs
Instantiate(enemyPrefab, spawnPos, Quaternion.identity);
_currentEnemyCount++;      // ← 怪物死了没人减
```

**问题**：`_currentEnemyCount` 永不回落，刷满 `maxEnemies` 后**永久停止刷怪**。

**建议**：怪物死亡时通过 `EnemyDieEvent` 回调减计数，或改为维护一个 `List<GameObject>` 并定期清理 null。**本阶段建议顺带修掉**，否则小螃蟹没法连续测试。

### 9.3 🟡 `CharacterEntity` 依赖存档数据

```csharp
public CharacterData SaveData;    // 怪物不需要存档
_combatAttr.Initialize(BaseMaxHp, saveData.CurrentHP, ...);  // ← 会空引用
```

**问题**：怪物没有 `CharacterData`，直接复用会报空引用。

**建议**：新写 `EnemyEntity`（只读 `CharacterDefine`，不涉及 `SaveData`），或给 `CharacterEntity` 加一个"无存档模式"。**推荐前者**，职责更干净。

### 9.4 🟡 数据表里没有螃蟹的条目

你当前的 `CharacterDefine.txt` 只有 `MC17 / MC19 / CapsuleEnemy`，**没有 Shell**。

**建议**：新增一条，例如：

```json
"2001": {
  "TID": 2001,
  "Name": "Shell",
  "MainType": "Monster",
  "SubType": "SwordAndShield",
  "Resource": "Prefabs/Monsters/Shell",
  "HP": 100.0, "AD": 10.0, "DEF": 10.0
}
```

> ⚠️ **注意**：`SubType` 必须与 `AttackDefine.txt` 里的 `ComboGroup` 完全一致，否则查表失败（你之前 MC19 的 `SowrdAndShield` 拼写错误就是这个坑）。
> 若希望螃蟹走**独立**的攻击配置，建议新增一组 `ComboGroup: "Shell"` 的攻击定义，避免和玩家武器组混用。
